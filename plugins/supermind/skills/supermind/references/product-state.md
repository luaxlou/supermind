# 产品状态

产品状态是后续工作确实需要的最小长期材料，不是需要永远维护不变的初始意图。记录当前认知及其依据；新证据改变认知时更新相关部分。

- **需求基线**：当前确认范围内的用户目标、范围、业务规则和验收条件。已确认的承诺与已实现、已验证的事实分开记录。
- **设计基线**：承接需求的现行模型、接口、系统及 UI 设计决定。UI 基线不能替代需求基线；没有 UI 的需求仍需设计与验收对应。
- **UI 基线与需求的依赖**：以本次范围已确认的需求基线为依据，将确认后的线框图作为 UI 设计基线，表达页面结构、信息和交互。它为后续视觉深化与实现提供对照；需求变更先更新需求决定，再处理受影响的 UI。缺少必要需求时只能形成探索草稿，不能自行标为已确认基线。
- **场景**：用户所处情境、意图、操作和可观察结果。
- **功能**：完整的用户可见能力，可以参与多个场景。
- **行为契约**：输入、规则、输出、边界和用户可见的失败行为。
- **能力**：具有清晰用途、适用情境、通用边界和真实载体的可复用成果，包括实现和工程实践；能否进入能力库还需符合实际接口、价值与确认要求。
- **证据**：支持某项产品行为或质量声明的可观察结果。

新产品先建立一个有价值的完整使用场景作为主线；不意味着后续每次改动都要重新设计整个产品。

已有产品先定位受影响的状态，只更新本次涉及的场景、功能、契约、能力和证据。局部实现调整不一定需要修改长期产品文档。

进入设计时按[设计阶段语境](design-stage.md)一次加载两项方法和项目基线。先检查当前范围是否具有足以支持设计的需求依据；缺失时明确目标、范围、规则、验收和待决事项。整个阶段持续使用已加载语境，不逐动作重新查询基线方法，也不重新确认同一决定。设计暴露新业务规则或需求变化时，更新需求及受影响的模型、接口、UI 和验收对应；纯视觉变化不自动重做需求。按明确授权处理变更，不把基线当成不可修改的最初目标。

优先沿用仓库现有目录和格式。如果还没有长期产品文档，而新认知会被后续工作需要，可在 `docs/product/` 下建立简洁记录，例如 `baseline.md`、`features/<name>.md` 或 `capabilities/<name>.md`。只创建产品实际需要的文件。

设计与实现计划保留在产生它们的任务方法中。将其中的产品决策提炼为产品状态，不复制整段任务记录。

只有新认知将影响后续工作、需要跨任务使用时才沉淀，优先更新已有资料。一次解释、尚未验证的猜想或没有通用收益的局部经验，不自动产生长期文档和能力条目。项目事实与通用经验分别表达，文档沉淀不等于能力入库。
