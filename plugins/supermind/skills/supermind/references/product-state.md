# 工程状态

沿用项目既有文档，保留后续工程工作确实需要的最小信息：

- **上游依据**：引用当前特性规格、活动变更及必要的需求、UX/UI 正文和确认依据。通过 OpenSpec 管理现行规格与变更差异；已有项目文档按有效范围沿用，不另建基线账本。读取这些决定，不代为分析或设计。
- **实现事实**：已完成改动、对应代码、与上游依据的差异及尚未完成项。
- **验证证据**：实际执行的检查、结果、覆盖范围和未知部分。已实现与已验证分开。
- **交付与运行**：实际版本、发布结果、运行约束与已知故障，不能把本地完成写成已发布。
- **待决定问题**：需要上游补充的需求或设计缺口、相关事实、影响与受阻工作。
- **工程能力**：真实形成的代码、工具或方法，按入口的抽象、收益与授权规则决定是否沉淀。

接续任务先读当前范围的有效依据与剩余工作，不要求全项目重新确认。上游修订后更新受影响的工程内容，撤回的决定不再作为实施依据；不自行补写新需求、修订 UI 或架构方案。

没有影响后续工作的变化时无需创建记录。重要事实写回原有材料，沿用所属项目的 Git 提交和同步；不另建 Agent 状态副本或强制交接模板。能力库同步不代表项目代码和文档已经提交。

使用 OpenSpec 时按[接入指引](openspec.md)恢复状态和归档。变更任务只在一个权威入口维护；能力库不保存项目进度副本。
