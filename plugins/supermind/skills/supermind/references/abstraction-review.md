# 从经验到可复用能力

当用户要求沉淀、提取或修正可复用经验时，在编写共享产物前、入库前和交付前使用本指引。它也适用于技能、模板和插件中承载的方法，不只适用于能力库记录。

## 先确定交付对象

用户要求可复用经验，交付对象就是可独立采用的方法或资产。发现来源、整理笔记、注册候选和更新状态都是可能的中间动作。即使工具返回成功，也不能把这些动作当成抽象任务完成。

用户只要求收集线索时，按来源观察处理，不宣称可直接复用。原始私有材料留在所属项目；抽象未完成不构成把它们同步到共享候选区的理由。已有开源工具有自己的独立资产，不必为了满足“提取”形式复制一份来源能力。

## 把案例中的决定变成方法

从实际解决的问题开始，逐项分辨：

- **为何有效**：哪个动作改变了什么结果，依据是用户反馈、实际行为还是推测？不能把同时发生的结果全归因于方法。
- **保留什么**：换一个业务仍成立的约束、输入输出与决策原则。
- **由采用方提供什么**：角色、业务规则、状态、数据来源、布局、环境及授权。不得从原案例偷偷补齐。
- **什么时候不用**：成本超过收益、前提缺失或方法无法解决的问题。
- **怎样开始和结束**：从采用方现有材料出发的第一步、关键分歧的处理、可观察的完成依据。

共享正文必须表达这些内容，但不要求机械增加同名章节。只有空白模板而没有采用方法，或只有原则而没有可操作的判断，不足以交付。代码和工具还需要真实获取入口、可配置边界及接入契约；方法正文可以自身就是完整资产。

## 对实际产物做迁移推演

审查时只使用拟交付的正文、它声明的可获取依赖，以及一个不同业务的采用方输入。不要回看原案例替它补全说明。

1. 给出具体但虚构的目标情境和输入，沿方法产出一个可审阅的小结果；不要只写“另一个项目也适用”。指出哪些步骤来自方法，哪些事实必须由采用方提供。
2. 改变一项原案例容易被固化的假设，例如角色、状态归属、页面数量或承载方式，检查能否通过已声明的配置边界处理。若必须改写核心方法，缩小适用范围或继续抽象。
3. 给出一个不适用或应拒绝的情境，解释停止或裁剪的依据。方法不能对任何问题都给出同一种流程。
4. 找出推演中的信息缺口：需要原作者解释、需访问私有材料、隐含行业状态机、未说明的依赖或缺失的完成标准。补齐正文后重看受影响的推演。

推演只是内容审查，不是实际接入，不记录 `complete-reuse`，不伪造工时或收益，不声称已通过真实跨项目验证。重大不确定性不能靠审查者填写 `approved: true` 消除。

## 把证据用在正确的地方

保留简短审查依据：被审查的具体正文或内容摘要、推演输入和产出、发现并解决的缺口、尚存限制。沿用任务记录或项目现有审查文档即可；共享能力里只留通用采用所需内容，不复制审查过程、私有案例或内部标识。

正文、契约、配置边界或必要依赖变化后，旧审查不自动覆盖新产物。先比对变化，再复查受影响部分，不因改了无关文案重跑全部工作。

区分四个判断：

| 判断 | 可以证明什么 | 不能证明什么 |
| --- | --- | --- |
| 隐私和结构检查 | 已覆盖模式未命中，必要字段存在 | 业务耦合已解除 |
| 迁移推演 | 在给定情境下，方法可理解、可开始执行且边界明确 | 真实接入成功或节省工时 |
| 原案例实践 | 该情境中的观察和反馈 | 所有项目都适用 |
| 真实采用结果 | 特定采用中的行为、成本和收益 | 新场景已获授权 |

## 入库和交付

用户已授权沉淀或修正的范围内直接完成工作，不重复索取许可。需要用户决定实质范围时，提供已经准备好的具体产物。真正采用到另一个项目仍遵守每次复用的授权规则。

入库前完成上述审查。`evaluate` 和 `complete-implementation` 只做字段、价值估计与登记检查，没有执行语义审查。返回 `null` 是未登记；返回能力记录是已登记，二者都不是抽象审查结论。`pending` 不可充当共享原始材料的豁免或沉淀完成的替代证明。

库内 `abstracted` 状态还有独立来源与成功证据要求；不为凑齐字段而新建原项目副本，不把推演包装成运行验证。内容审查已完成但状态条件未满足时，如实保留状态和限制。若接口无法表达真实产物，报告具体缺口，不伪造记录绕过。

登记后读实际生成的能力卡，确认它与已审查正文一致、采用入口有效，且没有混入本机出处或案例细节。交付时分别说明产物、登记结果和证据边界；不能只说“已入库，所以元能力已修复”。
