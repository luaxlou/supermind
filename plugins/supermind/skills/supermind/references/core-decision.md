# 工程执行决策

Supermind 在 Codex 中承接工程任务和重要反馈，依据当前请求、有效授权、上游成果及真实执行结果决定下一步。

## 判断与推进

1. **确认范围。** 实现、调试、验证、交付、运维、迁移退出以及工程能力复用属于本能力。需求分析和设计交回上游，不因发生在工程期间而重新纳入。
2. **承接依据。** 按[上游成果承接](implementation-input.md)读取已有需求、设计、源码与运行事实。资料足够时直接推进；不为接续创建完整项目档案。
   需要组织规格变更或恢复实施时，按 [OpenSpec](openspec.md) 直接读取官方 CLI 指令及项目活动变更，沿用唯一任务记录。
3. **识别缺口。** 缺事实则调查，缺实现则执行，缺结果依据则按授权补充必要验证。需求与设计缺口整理后交回用户或 ChatGPT，暂停依赖部分。
4. **选择工程能力。** 按[工程场景](scenarios.md)到达规定时点时完成检索或沿用有效结果，再按[能力调用指引](capability-routing.md)调用。检索失败不能解释为空库并自行新建。
5. **在授权内完成。** 常规工程行动连续执行，不逐步索取确认。复用与外部操作遵守已有授权边界。用户要求人工验证或暂不验证时不自行追加检查。
6. **依据结果继续。** 对照当前范围与验收依据，足够则交付，不足则继续；新的上游决定改变范围时调整受影响的工程工作。

实施计划只拆解既定方案、依赖和验证步骤。常规代码细节沿用仓库约定；需要改变业务规则、系统边界、接口契约或用户体验时，提供工程事实与影响，等待上游决定。

## 承接与反馈

收到“继续”时，读取最新有效依据、实现结果和剩余问题，沿用已有授权。新消息通常是对当前工作的补充或修正，明确切换任务才切换上下文。

工程结果需要跨任务使用时，按[工程状态](product-state.md)更新原有材料，沿用现有 Git 和同步机制。一次工具成功只说明调用完成，不证明功能达标；未知与实际结果分别表达。

工程能力来自真实使用与反馈。用户要求沉淀经验时按[从实践到可复用能力](abstraction-review.md)整理已有成果，不额外制造演练、证据或 Agent 状态系统。

未覆盖的工程情境根据进入条件、所需依据、授权动作和完成条件处理。涉及选择可复用工程能力时仍遵守检索规则；需求分析和设计不作为新场景扩展回来。
