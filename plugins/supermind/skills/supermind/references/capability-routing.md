# 工程能力调用指引

本文件落实[核心决策](core-decision.md)已经选择的动作。[场景指引](scenarios.md)决定进入条件和检索时点；本文件决定怎样调用现有能力及处理结果。先识别场景，再调用能力。

## 按需要选择

- 产品意图、行为契约、架构或用户体验存在未决项时，按[上游成果承接](implementation-input.md)整理问题交回用户或 ChatGPT，不调用需求分析或设计能力。
- 需求和设计明确、需要协调多个实施步骤时，使用工程规划方法；计划只拆解既定方案。
- 既有行为出现原因不明的问题时，使用系统化调试方法。
- 已有获批计划，且方法适合当前环境时，使用执行或委派方法。
- 选择验证范围、局部修复后复测、审查交接或发布验收时，先判断已有证据是否仍有效，以及尚缺什么证明。考虑内置的 [按风险与证据决定验证](../../proportionate-verification/SKILL.md) 技能；按影响范围补充测试与审查，不因阶段或代理变化重跑相同检查。必要检查及其故障阻断要求仍须遵守。
- 完成的仓库工作需要交付或发布时，使用集成与交付方法。
- 涉及专门工程领域时，使用命中适用条件的技能与工具；不通过领域能力间接执行需求分析或设计。

能力可以来自当前宿主、获准使用的插件或项目本身。选择前先应用用户与项目的禁用、排除和工程约束；已禁用能力不得通过另一能力的依赖、别名或间接调用重新启用。通用方法不应把可选供应方固化为运行前提。优先选择最贴合需要且被允许的能力，选定后遵守其说明。

## 能力库浏览

用户要求查看、解释、筛选能力或展示关系时，调用本地能力库启动器的 `inspect` 命令，依据其返回结果展示名称与说明，名称使用简洁的“中文名（英文名）”。不单列英文标识，不展示能力状态、状态分组或生命周期管理信息；详细说明保留官方项目链接、触发情境、接入方式和必要证据。

- “查看能力库”：`inspect --view overview --format markdown`；需要表格或筛选时使用 `--view table`。
- “打开能力库”：`open --format json`，同步、生成并验证展开的分类 README，再打开私有仓库。`render --format json` 只刷新文档，不打开浏览器。
- “清理某分组”：先用 `remove --category <root> --category <subgroup> --format json` 预览精确成员与引用。获得人工授权后，以 `--confirm --expected-digest <preview-digest>` 执行。需要避免再次自动导入时加 `--exclude-future`。这只清理库内条目，不卸载技能或删除源代码。预览过期或存在引用时阻断；保留历史，不强制删除依赖记录。
- “修改能力名称或说明”：调用 `describe --input <json> --format json`，输入文档包含 `capabilities` 数组，每项为 `{id, name, summary}`。保留原含义和范围；翻译不能让业务实现变为通用抽象。命令不改变契约、来源标识或验证声明，并同步生成文档。
- “显示登录能力”：从最新的完整检索或表格中确定标识，再调用 `inspect --view detail --capability-id <id> --format markdown`。
- “画出能力关系”：`inspect --view graph --format markdown`，按需要增加分类、生命周期、技术栈或能力过滤条件。
- “解释复用选择”：`inspect --view decision --input <decision.json> --format markdown`。
- “查看未满足需求”：`list-demands --format json`。之后有经过验证的实现满足需求时，调用 `link-demand --input <link.json> --format json`，输入仅包含 `observation_id` 和 `capability_id`。

`inspect` 只读；`open` 和 `render` 可能提交并同步生成视图。不能用扫描源文件代替这些视图，也不能用自行总结掩盖能力库退出码 `3`。

决策视图只是建议。先评估业务无关的抽象和正向净收益，每次具体复用或适配前取得人工确认。入库、验证通过或过去获批都不代表本次获授权。

决策视图与 `begin-design` 使用同一契约门禁：已声明契约完全匹配时可建议复用，部分匹配需要适配，零匹配即使排名第一也要拒绝。未声明契约时，经过验证且收益为正的能力仍须通过其他条件。运行环境、平台、许可证、技术栈、分类、当前验证、来源可用性和生命周期都由同一决策引擎判断；浏览视图不能将工作流拒绝的结果提升为复用建议。

每条强制契约都必须覆盖，包括识别到版本范围之后的其他要求。元数据维度同时检查。关联候选必须具备当前有效的成功关系证据，并通过与直接命中相同的资格证明。安全绝对路径和规范 `file:` 地址共用可用性检查。

到达场景规定的检索时点时必须完成相应需求检索或使用仍有效的结果。权威记录变化允许最多三次一致性重试，与一次检索修复及完整重试独立计数。索引启用前评测真实语义和混合检索，并在清单中记录阈值与测量值。敏感信息在向量化、标识生成、历史存储和诊断前脱敏。

需求历史保留序列化事件类型 `unmet_observed` 和 `implementation_linked`。每项观察必须有创建事件，每项已关联观察必须有指向同一能力的关联事件。第二版结构缺少需求表或事件时报告 `authoritative_store_corrupt`，不能视为空库。有效日志可恢复已知历史，迁移不能凭空创造历史。

## 适用时使用 Superpowers

只有用户及项目允许时，Superpowers 才能作为可选能力来源；安装并不代表获准使用。禁用时不调用、不推荐恢复，也不将其缺失作为通用方法的阻断条件。允许使用时，`superpowers:writing-plans`、`superpowers:systematic-debugging`、`superpowers:executing-plans`、`superpowers:requesting-code-review`、`superpowers:verification-before-completion` 等技能可以满足相应需要。它们不是 Supermind 的前提、固定流程或运行基础。

采用前确认方法适用于既定方案的工程执行。包含强制需求分析、头脑风暴或设计前置流程且无法限定为工程范围的方法，不适用于 Supermind；使用当前可用的工程执行方式。上游需求与设计缺口交回用户或 ChatGPT，不以调用其他插件绕过职责边界。

## 避免不必要的调用

目标、影响范围和实现方式明确，且改动局部时，直接处理。例如准确的文案修改、已有配置调整或既有功能契约内的小改动。

工程任务不启动需求分析或设计流程。技术不确定性通过调查、工程规划或调试处理；需要上游决定的缺口按承接指引交回。

## 根据新认识继续

将结果与当前问题联系起来：新证据可能支持继续，也可能改变问题、暂停方案或完成本次解释。不要默认回到最初目标，也不要默认新话题已替代整个任务。依据最新对话和证据判断，只有会显著改变结果的歧义才需要用户澄清；只有出现适用条件时才调用能力。

详情页帮助判断是否适用、开始使用和避免误用：展示用途、获取入口、触发场景、接入方式与必要边界，只保留一个页面标题。正文保留段落、列表、独立链接和代码块。不用“契约”等元数据栏目包裹完整说明，不展示内部评分、验证流水账、使用方和需求管理记录，不生成空栏目。审计数据保留在底层；会影响正确使用的限制应写入使用说明或条件。目录和详情均复用 GitHub 与 CLI 的同一呈现逻辑；交付前读取生成后的完整页面，不能只检查字段或同步结果。
