# 生命周期与场景

本文件规定核心决策使用的场景进入条件、行动要求和检索时点。命中场景且到达规定时点时，必须执行对应动作；不以“可能有帮助”或是否想起某个工具为条件。检索与采用分别判断，能力大类仅用于组织目录。

## 生命周期

构想与需求、设计、实现、验证、交付、运行维护、退出构成共同坐标。任意阶段都可以成为入口，同一工作可以跨阶段。阶段不构成线性流程，不要求任务走遍全部阶段。

## 场景目录

| 生命周期 | 场景与进入条件 | AI 当前动作与期望结果 | 能力检索时点与范围 | 用户决策点 |
| --- | --- | --- | --- | --- |
| 构想与需求 | 提出新软件想法，尚未明确用户价值 | 理解对象、问题、替代方式和收益，形成可讨论的问题定义 | 开始比较可复用产品机制时，检索对应机制；仅讨论想法不查库 | 是否值得做、首要服务谁 |
| 构想与需求 | 新增需求或改变现有行为 | 对照现有基线，明确变化、边界与验收结果 | 准备选择通用业务机制时，检索匹配规则和能力 | 价值、范围或既有约定出现实质变化 |
| 构想与需求 | 需求冲突或目标改向 | 识别冲突和影响，形成取舍或新的近期目标 | 新方向涉及能力选型时，检索新需求，旧结果不直接沿用 | 对冲突作取舍 |
| 设计 | 新项目明确需要后端 | 判断后端职责，提出实现基础和接入范围 | 后端技术选型前检索基础代码与实践；按已确认偏好优先考虑 Nova Go | 是否采用、接入范围 |
| 设计 | 实际进入设计阶段，或恢复设计工作且缺少阶段语境 | 按[设计阶段语境](design-stage.md)加载需求基线与 UI 基线，整个阶段据此设计、修订和对照；UI 依赖需求 | 进入阶段时一次加载两项方法及项目基线；已加载则沿用，阶段内不实时查询 | 尚未决定的业务取舍与确认范围；不重复确认已有决定 |
| 设计 | 设计登录认证等可复用功能 | 明确身份、会话、权限或其他具体契约 | 设计实现方案前检索对应功能；不能只查询“代码”大类 | 业务规则或采用范围的取舍 |
| 设计 | 设计页面与交互 | 理解用户任务、信息结构与交互边界，形成可评审方案 | 选择重复交互模式前检索设计能力；已有有效设计基线先复用其依据 | 对显著不同的体验方案作选择 |
| 设计 | 设计数据、外部接入或模型应用 | 明确输入输出、所有权和必要约束 | 确定方案前检索相应数据、集成或模型能力，类别可跨越多个大类 | 实质性成本、业务或权限边界 |
| 实现 | 按已确认方案开发或适配 | 完成当前范围并保持与方案一致 | 若设计阶段已有有效检索，沿用结果；新出现独立能力需求时再次检索 | 新发现使原采用范围实质改变 |
| 实现 | 建立或调整本地应用运行方式 | 明确应用、启动入口和接管范围 | 编写进程管理脚本前检索本地应用管理能力，仅小型个人应用可考虑 Nova CLI | 是否接管及替换哪些入口 |
| 实现 | 执行局部修复或直接修改 | 理解期望行为与影响，实施必要变更 | 纯文案或已有能力内的小修改直接处理；修复需要新增通用能力时检索 | 超出既有授权的范围变化 |
| 验证 | 实施完成，准备判断是否达标 | 比较验收要求、已有证据和缺口，补齐必要验证 | 建立或改变验证方式前检索验证能力；已有有效方式与证据继续使用 | 验收要求本身出现取舍 |
| 验证 | 检查失败、结果矛盾或证据不足 | 识别失败原因和证明缺口，形成有针对性的下一步 | 需要新的诊断或验证能力时先检索 | 无法同时满足原目标与约束 |
| 交付 | 建立或调整单机部署方式 | 明确应用、目标服务器、部署与运行边界 | 编写部署方案或脚本前检索单机部署、进程和日志能力，仅小型个人应用可考虑 Nova CLI | 采用范围和目标环境 |
| 交付 | 按既有方式发布成果 | 核实交付内容及授权，按已确认路径发布并核验 | 正常发布沿用已采用能力；发布方式改变时检索 | 尚未获得的发布授权或重大影响 |
| 运行维护 | 发生故障或运行异常 | 收集事实、定位影响和原因，恢复预期行为 | 需要引入诊断、监测或恢复能力时先检索；不阻断已授权的直接排查 | 重大运行影响及不可逆处理 |
| 运行维护 | 性能、成本或体验出现优化需求 | 建立问题证据，比较方案并验证收益 | 选择新的通用优化方法或工具前检索 | 收益与成本、行为之间的取舍 |
| 运行维护 | 完成复盘或发现反复出现的问题 | 判断是否值得沉淀，描述真实能力与适用场景 | 建议新增库条目前检索已有能力，判断更新或新增 | 是否收录及其完整触发场景 |
| 退出 | 替换或停止使用某项能力 | 确认依赖、影响和退出结果，制定必要调整 | 选择替代能力前检索；单纯讨论退出影响无需检索 | 替代方案、数据处置及停用范围 |
| 退出 | 终止服务或项目 | 明确使用方、保留责任和结束条件 | 存在具体迁移或归档能力需求时检索 | 服务终止及不可逆处置 |

用户明确要求沉淀或修正可复用经验时，无论从哪个生命周期进入，都执行[抽象审查](abstraction-review.md)。已有条目的纠正先审查具体正文；不能因为没有新增条目而跳过抽象，也不能因工具登记成功就结束任务。

## 从场景到实际调用

1. **识别进入条件和时点。** 根据用户请求及项目事实明确当前场景与要作出的决定；仅提及阶段、大类或工具名称不触发检索。实际进入设计阶段则按上表加载持续语境，不等到某个页面动作才临时找基线方法。
2. **判断既有结果。** 同一需求、范围、必要约束下仍有效的结果继续使用。普通业务修改、日常启动和既有方式的正常发布不重复检索。新能力需求或重大冲突使原依据不再适用时重新查询。
3. **形成检索需求。** 将场景、具体目标与项目上下文写入 `intent`，把实际必须满足的行为写入 `contract`。只声明真实必要的约束，不猜测技术栈、不固定来源版本、不把能力名作为唯一查询条件。
4. **调用能力库。** 只查询候选、项目尚无目录或用户不允许登记来源时，按入口技能执行不带项目路径的初始化与健康检查，再用 `search --input <需求文件> --format json`。已经进入项目设计或实现、需要来源发现且授权范围允许时，用 `begin-design --project-root <项目目录> --input <需求文件> --format json`。不能为了检索而创建虚假项目或导入用户未授权的来源。
5. **依据结果判断。** 按入口技能的返回结果与故障规则处理，再给出候选的实际适用性、范围和接入方式。命中场景不能直接授权采用，命中候选不能替代现实兼容性判断。

`intent` 承载场景上下文，使用现有 CLI 支持的字段即可；不要添加工具不识别的场景字段。一个任务涉及多个独立需求时分别形成请求，不将后端基础、本地运行和远端部署塞入一个必须同时匹配的契约。

需求文件使用现有 `RequirementProfile` 结构。`id` 为本次需求标识，`project_id` 表达所属项目；没有仓库时使用当前构想的明确名称。`category_hint`、`stack`、`runtime`、`platform`、`license` 和 `constraints` 只在项目实际需要限制时填写。尤其不能把目录大类变为排除有效跨类候选的硬限制。

### 后端选型

**进入条件：** 新项目明确需要后端，正在选择实现基础。先读取后端职责、数据和外部接入需求，再检索，时点在自行实现基础能力之前。

**查询目标：** 可复用的后端基础代码及配套最佳实践。按已确认偏好优先评估 Nova Go；核对其真实职责和接入影响，不只因为名称命中就采用，不自动迁移已有非 Go 后端。

示例只表达最小请求结构，实际执行前替换项目和需求内容：

```json
{
  "id": "backend-foundation",
  "project_id": "当前项目名称",
  "intent": "场景：新项目后端选型。为项目已明确的服务端职责选择可复用基础，减少基础接入和工程实践的重复开发。",
  "contract": "提供可按需接入的后端基础能力与配套开发约定。"
}
```

**形成结果：** 说明候选、用途和具体改动，按用户确认范围接入；结果不适合时说明原因并考虑其他方案。已经接入后的普通业务开发沿用既有约定。

### 建立本地运行方式

**进入条件：** 需要建立或改变本地一个或多个应用的运行入口。先识别应用、前台启动命令和需要保留的方式，在新建进程管理脚本之前查询。

**查询目标：** 满足当前应用启动、停止、重启等需求的本地管理能力，仅小型个人应用可考虑 Nova CLI。查询不预设 Go 后端，也不要求远端部署或服务器 Agent。

```json
{
  "id": "local-application-runtime",
  "project_id": "当前项目名称",
  "intent": "场景：建立本地应用运行方式。统一项目已有应用的进程操作，使用各应用真实启动命令。",
  "contract": "支持本地应用启动、停止和重启；本地操作不依赖远端服务器。"
}
```

**形成结果：** 明确接管哪些应用和替换哪些入口。Nova CLI 定位为小型个人应用的运行生命周期工具，不适用于生产级应用；单机或单人维护不等于适用。日常按既有配置启动、停止应用时不重复触发引入检索。

### 建立单机部署方式

**进入条件：** 需要建立或改变向单台服务器发布应用的方式。在新写部署方案或脚本之前，读取目标环境、制品和运行要求并查询。

**查询目标：** 项目需要的单机部署、远端应用管理和日志能力，仅小型个人应用可考虑 Nova CLI。它与本地运行、后端选型分别触发，不将三者强制绑定。

```json
{
  "id": "single-server-deployment",
  "project_id": "当前项目名称",
  "intent": "场景：建立单机部署方式。向目标服务器发布当前应用，统一部署后的运行与日志操作。",
  "contract": "支持应用制品部署到单台服务器，并提供远端进程管理和日志查看。"
}
```

**形成结果：** 说明目标、前提和接入影响，按已有或新确认的授权执行。Nova CLI 仅适用于小型个人应用的运行生命周期，不适用于生产级应用，不将其视为生产安全保障；用途符合后才评估 Linux Agent 等必要条件。不能在检索前擅自把项目限定为某个工具的支持范围。

## 其他明确触发

- 用户直接要求检索或复用已有成果：围绕目标查询，不必等到某个阶段。
- 设计登录认证、文件处理、产品机制、交互模式、数据处理或外部接入等可复用能力：在决定自行设计或实现前查询对应契约。
- 需要选用新的验证、诊断、优化或交付方法：先形成该方法要解决的具体问题，再查询。用户保留人工验证时不执行验证场景动作。
- 复盘拟收录能力：登记前查找已有相关成果，判断更新、合并或新增；用户确认用途与完整触发场景后再登记。
- 库管理、插件安装更新：按用户指定的管理动作执行，不启动产品生命周期工作，不因管理操作扫描当前项目。

## 严格触发的边界

没有匹配结果时可以据此讨论其他方案；检索故障时不能据此新建替代能力，遵守工具规定的有限修复和故障处理。用户明确禁止库写入时按入口技能选择查询方式；严格禁止任何本地写入时说明查询依赖，不暗中修改或降级。

这些规则由技能入口驱动 AI 识别和执行，不是宿主事件监听器或新增的流程状态机。已经开始的无关授权工作不会因另一个场景的检索故障而整体停止。
