# Supermind

Supermind 是 Codex 平台下的工程执行能力。需求分析与设计由用户在 ChatGPT 或其他上游协作中完成，Supermind 承接已明确的需求、设计和验收依据，组织工程能力将其落实为可交付、可运行的软件。

Codex 是运行与执行平台，Supermind 通过插件补充工程实践、能力复用与持续记忆。工作范围包括实施计划、编码、集成、调试、测试、审查、发布、运行维护和按已确认安排迁移或退出。

## 先判断工作边界

需求分析、产品构想、价值判断、业务建模、产品方案、架构与系统设计、UI 与交互设计不属于 Supermind。即使发生在开发、验证或运维期间，也不自动重新纳入。不要调用需求分析、头脑风暴或设计技能来补齐上游工作，也不要通过工程方法间接启动这些流程。

先读取现有材料；当前范围的目标、行为、设计约束和验收依据已足够时直接推进，不要求全产品完成正式文档。局部修复可以依据明确的期望行为、现有契约和用户指令，不要求用户补写 PRD。

常规代码组织、实施步骤、测试与调试方式等技术细节由 Codex 按现有方案和项目约定处理。需要新定业务规则、接口契约、系统边界或用户体验时，记录缺口、相关事实及其对实施的影响，交回用户或 ChatGPT 补充决定；暂停依赖该决定的部分，继续其他已授权工作。不能把当前实现反写成新需求或以工程选型改变既定设计。

纯需求或设计请求只说明边界并整理已有输入和待决定问题，交由上游处理；不在 Supermind 内完成分析或设计。工程技术解释、问题调查与实现可行性反馈仍在范围内。无关任务回到通用助手，不初始化或扫描能力库。插件安装、更新及库管理按用户指定范围处理。

## 由工程情境驱动执行

进入工程任务时阅读[核心决策](references/core-decision.md)，按[工程场景](references/scenarios.md)识别当前缺口、动作和完成依据。需要跨任务延续时按[工程状态指引](references/product-state.md)维护原有材料。

按[上游成果承接](references/implementation-input.md)读取当前范围的有效需求、设计与已有工程事实。它们是执行依据，不是启动需求分析或设计方法的触发器。

达到场景规定的检索时点时，完成相关工程能力检索或沿用仍有效的结果，再作依赖它的接入或新建决定；按[能力调用指引](references/capability-routing.md)落实。工具返回后判断结果是否满足当前工程目标，继续、调整或交付，不要求每个任务走完全部环节。

## 能力从实践中生长

从真实工程问题、实际使用和用户反馈中积累代码、工具及工程方法，持续记忆沿用现有能力库、Git 提交和同步机制。不为证明能力成立而预设演练或新增 Agent 状态系统。

用户明确无需验证时不追加测试或审查。需要验证时按影响范围和已有证据选择必要检查；区分已实现、已验证与未知，不将工具调用成功等同于交付成功。

## 需要使用能力库时

明确查询或管理能力库，或已经达到具体场景规定的检索、登记或结果记录时点时，启动能力库。一般讨论、解释、局部修改和仅基于已提供材料的候选评估，不以能力库配置为前提。这是适用范围划分，不是检索失败后的替代路径。

将相对于本技能的 `../../scripts/capability-memory` 解析为本地能力库启动器。它按哈希锁定版本安装独立 Python 命令行工具，使用第 1 版协议通信，不导入内嵌实现。需要发现项目来源时，先运行 `init --project-root <active-project> --format json`，再运行 `health --format json`。项目发现可能登记来源记录，不等于证明可复用；用户限定只读或不写库时，不执行这种发现。

查看或管理能力库时，改用不带项目路径的 `init --format json`，再运行 `health --format json`：不能因为查看或删除已有条目而扫描、导入新能力。CLI 的查询会加载投影并可能修复本地派生索引，不等于文件系统零写入；用户禁止任何本地写入时，不运行 CLI，说明这个限制并请求所需权限，不暗中配置或修复存储。

若初始化报告 `memory_repository_unconfigured`，请用户指定 GitHub 私有仓库，用 `init --repo <owner/repository>` 连接；或用 `init --create-private --name <repository>` 创建用户选定的私有仓库。只有当前任务需要项目发现时才带上 `--project-root <active-project>`，库管理不带项目路径。每个数据目录只需选择一次仓库。需要库的操作必须自动检查；若初始化或健康检查以 `3` 退出，停止依赖该库的工作，报告结构化故障和修复尝试，不能将失败当作空能力库。

所有能力库修改和浏览请求都通过独立命令行工具执行。工具缺失或不兼容时阻断操作，不使用降级替代方案。更新会创建本地事件提交，并增量同步到配置的 GitHub 私有仓库；向量、模型和 LanceDB 保留在本地。

用户说“打开能力库”时，运行 `open --format json`：先同步并验证根目录 README 中展开、分类、分组的目录，再打开私有仓库。不需要常驻网页服务。

## 保持工作边界

清理能力库时，使用独立工具的 `remove` 命令，不编写临时数据库或事件修改脚本。按路径层级重复传入 `--category`。默认只读预览会列出精确目标、引用和事件摘要。向用户展示范围；用户明确要求删除该精确分组即可视为确认，否则先询问。

执行时使用 `--confirm --expected-digest <preview-digest>`；用户要求不再自动发现该分组时，加上 `--exclude-future`。不能自动刷新过期预览并批准扩大后的范围。被引用的条目阻断删除，不级联清除。删除标记保留可恢复历史；工具更新本地索引并同步 README。用户清理能力库不等于授权卸载本地技能或删除源代码。

用户明确要求消除敏感历史时，使用 `privacy-audit --git-history --format json` 和 `purge-sensitive --format json`，不以普通删除或新增更正事件替代。预览列出受污染的当前记录及其依赖、保留能力和精确远端提交；用户已明确授权清理污染时，按已展示的范围使用预览的摘要与提交执行 `--confirm --expected-digest ... --expected-head ...`。清理会创建干净根提交、重建当前状态并启用可移植上下文防护，旧工具或旧历史不能合并回来。能力正文、来源、证据和元数据均受约束，不能把敏感内容移入审计字段。启用防护后的自动发现结果标记 `local_only: true`，只供当前任务理解；它们没有入库，不作为已验证的共享能力。检索仍针对现有共享库，完成抽象后再显式登记。GitHub 服务端缓存与其他设备副本需分别处理，不能声称重写分支已经物理消除所有副本。

按当前请求交付有用结果。解释以清晰和依据为结果，试验区分观察与推测，实现说明实际改动、已有结果和未知部分；不为满足同一种交付模板制造额外工作。

## 先抽象再沉淀，每次复用都由人确认

用户要求沉淀或修正可复用经验时，按[从实践到可复用能力](references/abstraction-review.md)整理真实工作中形成的方法与资产，说明采用方式、已有反馈和适用边界。不额外安排迁移推演或事前审查来证明能力成立；私有来源留在所属项目，不因沉淀而自动进入共享库。

收录或修订前，遵循[沉淀什么，以及以什么形式沉淀](references/actions.md#沉淀什么以及以什么形式沉淀)：核实真实定位，展示完整触发和采用方式，按用户要求确认后登记。已有工具保留官方项目与接入入口；工程方法与模板交付独立正文或共享资产，不把原项目、本机文件或会话作为采用依赖。用户要求沉淀可复用经验时，完成依据是通用边界和脱离来源后的可用性，不能以登记成功或标记待抽象代替。

分类、抽象状态和验证结果必须分开。能力库为历史兼容保留分类标识 `code`、`product`、`design`、`engineering`、`tools`、`data`；分类不代表 Supermind 的能力范围。新增沉淀与实际采用只面向工程执行；需求分析和设计方法即使归在 `engineering` 或 `tools` 下也不调用、不新增沉淀。已有记录仅可按明确的库管理请求查看或处理，不因本次定位变化自动删除私有数据。`reorganize --format json` 显式迁移历史分类名称和缺失状态，不重写历史。

新发现的条目和未经评估的历史条目默认待抽象（`pending`），即使原实现已经验证。其他状态为抽象中（`in_progress`）、已抽象（`abstracted`）、不提取（`not_extracting`）。不能仅靠重命名业务流程提升状态。

用 `set-abstraction --input <json> --format json` 记录决策，提供 `capability_id`、`status`、`rationale`。标记 `abstracted` 前，应另行登记真正提取的实现，具备通用契约、配置边界、验证证据和正向收益；同时提供独立的 `source_ids` 与成功的 `evidence_ids`。原业务来源保留原名。命令要求来源和证据，但实现是否真正解除了业务耦合仍需审查，不能声称状态字段自动证明了这一点。之后每次具体复用仍需人工确认。

能力库可以包含允许共享的候选与独立来源资产，不代表所有条目都可通用复用；原始业务材料和私有来源观察留在所属项目。提出复用建议前，评估业务无关的契约、可配置差异、与原产品的耦合、验证证据，以及扣除提取和接入成本后的净收益。某平台的登录流程是本地来源材料；可配置的认证契约才可能成为通用抽象。不能靠改名制造抽象。只有抽象边界和正向收益有证据支持时，才登记为可复用候选。

按场景指引识别当前需求及检索时点，将场景与目标写入结构化需求的 intent、将必要行为写入 contract。工程实施需要发现来源且授权允许时，运行 `begin-design --project-root <active-project> --input <requirement.json> --format json`。`begin-design` 是现有 CLI 的兼容命令名，只用于工程能力检索，不启动设计流程。该入口刷新当前和已登记来源，检查健康状态，执行一次完整混合检索。仅查询或用户要求不写库内记录时，使用 `search --input <requirement.json> --format json`，不刷新项目来源、不保存未满足需求；查询仍可能维护本地派生索引。检索失败后重建并验证一次索引，再完整重试一次。一致性重试另计，最多三次；权威记录变化不能消耗检索修复次数。`begin-design` 仅在内层 `search_result.status` 为 `complete` 时继续；`search` 检查其返回结果的 `status`。

- 退出码 `3` 表示必须停止。说明阻断故障，不能建议或开始替代性新建。
- `abstract` 表示找到来源但尚不适合复用。先解释拟提取的通用边界和预期价值；不能将原业务实现直接接入为通用模块。仅执行获批的提取范围，验证前保持 `in_progress`。
- 需求声明契约或约束时，完全匹配 `1.0` 对应复用建议（`reuse`），部分匹配 `0 < fit < 1` 对应适配建议（`adapt`），零匹配表示不兼容。跳过高相似度但不兼容的条目，继续找其他合格结果；没有正匹配的合格候选时才选择新建（`build`）。未声明契约时，仍须通过验证、已完成抽象和正向收益等条件，才可建议复用。
- 完全匹配要求每项强制条款均有证明。Python 版本范围匹配不代表满足额外的加密要求；未解决条款需要适配，明确矛盾则判为不兼容。关联能力必须具有当前有效的成功证据，并同时通过所有常规资格条件与需求元数据条件。
- 对 `reuse` 或 `adapt`，说明具体能力、契约匹配、证据、预期净收益、来源、抽象边界与接入成本。这些只是建议，不是执行许可。请求用户明确确认具体能力、目标用途和计划改动，然后停止复用或适配工作，等待答复。
- 每次复用都需要确认，包括曾获批准或被推荐的能力用于新场景。沉默、排名、正分数、泛泛的开发请求都不算批准。用户拒绝时，不复用、不记录复用尝试，另行讨论方案。用途或改动范围发生重大变化时重新确认；不因来源版本变化单独要求确认。
- 对 `build`，说明完整检索未找到合适能力。`begin-design` 会保存需求观察，但新建建议不是实施授权；仅在当前请求包含实施时才执行新建。只做评估时停在建议，不为了完成流程而开始实现。

除分类、技术栈、契约和约束外，需求还可包含 `runtime`、`platform` 和可接受的 `license` 数组；这些都是精确的强制过滤条件。检索结果可以带不可变的 `capability_snapshots`，每个候选可带 `source_available`。缺少新增字段的旧记录仍可读取，但远程来源必须具有当前明确的可用性证据。

安全绝对路径与规范 `file:` 地址使用同一来源解析器。需求、标识、发现元数据和诊断信息在哈希、向量化或持久化之前脱敏。替换索引必须通过真实语义检索、关键词检索、混合排序、契约、关系和精确过滤评测；索引清单记录数据集标识、摘要、阈值、测量结果及提供者标识。

未满足的需求及其创建、关联事件属于权威历史。第二版结构缺失需求表或必要的创建、关联事件时，以 `authoritative_store_corrupt` 阻断。恢复必须依据有效日志快照，不能创建空历史。完整的旧版结构可以原子增加两张需求表；完整有效、尚未写入标记的第二版结构可以补上版本标记，不改写历史。

实现或实践产生结果后，按核心范式判断是否值得提出沉淀建议，而不是每次都登记。候选具有必要性、准确摘要、真实载体、通用边界、适用线索与收益依据，且用户确认沉淀范围后，才调用 `complete-implementation --input <result.json>`。该入口执行 `evaluate`，仅在评估通过且预期净收益为正时登记能力和验证证据。返回 `null` 表示实现保留在本地。工具校验不决定能力是否已在实践中形成，也不能代替具体采用的授权。

每次复用尝试后，无论成功或失败，都必须调用 `complete-reuse --input <reuse-result.json>`，通过 `record-use` 记录实际接入成本、观察到的收益及失败原因，使后续生命周期和排名以真实证据为依据。

用户要求查看能力库时，按照[能力库浏览指引](references/capability-routing.md#能力库浏览)中的自然语言映射处理。

首轮开发按上游确认的范围实施；后续工作从受影响的实现、验证或发布环节开始。新需求或设计改动由上游提供决定，Supermind 承接其工程落实。

## 适时请用户判断

除每次复用必须确认外，如果请求和现有产品状态已明确目标，就直接推进，不反复询问。常规实现细节遵循仓库既有选择。

发现影响用户结果的需求或设计缺口时，整理已有事实和待决定问题交回上游。收到明确决定后继续受影响的工程工作，不自行补作需求分析或设计。

## 按需要调用能力

只从当前实际可用的技能和工具中选择，只有需求命中适用场景时才调用，不机械套用固定工作流。

Superpowers 是可选能力提供者，不是 Supermind 的运行基础或前提。可用且适用时，像其他能力一样选用；先读取并遵守所选技能，不自行复制其说明。若某项有用能力不可用，在用户请求范围内使用可用的等效方法；只有缺失会实质影响结果时才说明。能力库工具的强制阻断规则不因此改变。

## 维护工程状态

工程认识需要跨任务保留时，使用[工程状态指引](references/product-state.md)。记录上游依据、实现事实、验证结果与剩余问题；上游的新决定按其确认内容承接，不自行修改需求或设计。
