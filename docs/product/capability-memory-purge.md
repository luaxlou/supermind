# 能力库彻底清理

仅在用户明确要求不保留历史时使用 `supermind-memory purge`。普通删除仍使用 `remove`。

- 重复 `--capability-id` 指定精确条目；默认只预览。
- 预览列出关联记录、保留能力、远端提交和本地历史缓存路径。
- `--confirm --expected-digest <预览摘要> --expected-head <预览提交>` 执行已确认范围。
- 关联到保留能力的共享记录阻止清理，不自动扩大删除范围。
- 当前状态生成新的根提交，覆盖主分支历史；保留条目的当前证据继续存在，已删除条目的旧事件不再带入。
- 只允许在线、同步、干净且无额外远端分支或标签的能力库。使用精确远端提交保护，远端有新提交则拒绝推送。
- 清除当前库旧 Git 对象、旧索引代次和迁移暂存；源项目代码不动。下一次健康检查重建索引。
- 新的历史代次阻止旧设备合并；旧版工具不能读取新标记，其他设备需要升级并从新基线重新初始化。
- 推送结果不确定或本地切换中断时保留 `purge-pending.json`，阻止普通同步。先核验远端和暂存目录，不能删除标记后继续合并。

这不是对 GitHub 服务端缓存、外部克隆或系统备份的物理擦除保证，也不会擅自删除独立的旧版数据目录。

## 敏感历史清理与后续防护

`privacy-audit --git-history --format json` 检查当前记录、事件历史和本地全部 Git 对象（包括无引用对象），只报告条目与问题类型/数量，不输出匹配原文。检测包括个人目录、本机文件 URI、私有会话引用及其常见编码形式；不是任意商业敏感信息的自动识别器。

`purge-sensitive --format json` 预览保留当前干净记录、删除污染记录及依赖记录的计划。干净能力依赖待删除能力时阻断，不能静默扩大删除。引用被清除证据的能力取消已有验证声明；不能留下无依据的已验证状态。

执行预览后以 `--confirm --expected-digest <摘要> --expected-head <提交>` 应用。通过现有根提交重建机制清除旧 Git 历史，并在 memory.json 中写入 `portable-context-v1` 防护策略。该策略在事件落盘及同步生成提交之前检查全部新增记录，包括证据与元数据；在线与离线写入一致拒绝泄漏，不静默截断方法正文。远端与本地的策略不一致时阻断同步。旧工具不能理解新标记时必须升级，不得删除标记绕过。

启用防护后，自动发现返回 `local_only: true` 的本机观察，不再写入来源注册表、能力或审计历史；`begin-design` 仍会检索已有共享能力。只有另行整理、审查后的可移植资产才能显式登记，不能把观察结果冒充已入库。

防护策略由本次明确授权的敏感清理启用；既有库不会因普通只读查询而自动重写历史。其他尚未清理的库需要单独预览并启用，不能宣称安装新版就清除了所有库。

清理后使用安装版本核对：健康状态、能力清单、事件与 Git 对象扫描、远端分支标签、根提交无父节点。原始来源材料不再是复用资产；需要重新提取时只能按可移植内容重新评估，不能恢复旧历史。

依据：[GitHub 敏感数据清理说明](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。重写与强制推送不会保证服务端缓存、旧 SHA 访问或他人克隆被清除；服务端垃圾回收和缓存清理需要 GitHub Support 处理。未经授权不替用户发送支持请求。
