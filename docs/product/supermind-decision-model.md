# Supermind 顶层决策模型

状态：设计草案，待审阅；不是已实现能力的说明。

## 0. Supermind 自身的适用性准入

在生命周期、场景和能力钩子之前，先判断是否应进入 Supermind。它只服务于软件开发项目，不是通用任务执行入口。

进入必须同时满足：

1. 当前对象是明确的软件项目，或用户明确要创建的软件项目；已有仓库不是必需条件。
2. 当前请求直接服务于该项目的需求、设计、实现、测试、发布、运行维护或退出，或与之直接相关的工程文档、复用实践和工具链建设。

软件项目背景和当前任务关联都必须有可说明的依据。仅凭工作目录里有代码、安装了 Supermind、出现“设计／项目／文档”等关键词，或用户点名技能，都不能绕过适用性判断。

| 结果 | 行为 |
| --- | --- |
| 适用 | 记录判断依据，再收集开发情境并进入决策流程 |
| 不适用 | 不启动 Supermind，回到通用助手处理当前请求，不强行包装成软件开发任务 |
| 无法确定 | 只询问一个必要的范围问题；确认前不进入开发流程 |

不适用或无法确定时，不执行能力库初始化、健康检查、项目扫描、检索、记录或同步，不生成开发计划与项目文档。准入前只使用当前请求和已经提供的背景；必要的补充信息通过澄清取得，不为证明适用而遍历用户文件。

例如，为已有软件项目更新 README 属于适用任务；即使位于代码仓库中，写旅行攻略、处理私人事务或编写无关商业文案也不适用。用户明确要求新建一个应用时，可以在尚无仓库的情况下通过准入。

Supermind 的安装、更新或库管理请求应识别为工具管理操作，按明确范围处理，不因此启动软件开发生命周期编排。管理入口不能成为非软件任务进入开发流程的旁路。

实施时，技能发现描述负责准确表达适用范围，入口判断负责在任何开发副作用之前执行准入。仅修改介绍文案不能视为完成这一约束。当前技能中“每次调用先初始化”的要求必须改为“适用性准入通过后，按任务需要初始化”。

## 1. 目标与边界

Supermind 是基于 Codex 的产品开发协作插件。顶层指导不仅决定怎样执行工作，也决定哪些成果值得沉淀、以什么形式进入能力库，以及何时重新调用。

本设计将现有分散的行动类型、产品状态、能力准入和复用规则连接成统一决策体系。目标是减少重复劳动与组织成本，而不是增加流程、文档或库内条目数量。

采用“稳定指导＋结构化情境＋条件决策”的方式：固定流水线不能区分小改动与高风险操作；完全依赖临时推理又无法提供一致的准入和调用依据。AI 负责理解意图及解释语义，项目运行时负责验证明确条件和授权边界。

本轮只确定设计，不改运行时、已安装技能或能力库数据，不自动推广已有条目。

## 2. 顶层指导

- 以用户目标、实际收益和交付证据选择行动；成本包括理解、确认、执行、验证和维护。
- 延续已有产品与项目约束；没有实际需要时，不新增文档、流程或能力。
- 自动发现和提出建议不等于获得执行许可。每次具体复用都须人工确认。
- 来源材料、候选能力与已验证的通用资产必须区分；字段完整或分数为正不证明通用价值。
- 判断所依赖的资料失效、冲突或缺失时，明确报告，不将检索失败当作没有合适能力。
- 常规实践不能覆盖授权边界和安全限制。顶层规则冲突必须显式处理，不能通过排序分数消解。

这些指导随 Supermind 项目版本维护。能力库中的实践可以提出改进依据，但不得自行修改顶层规则来批准自己入库或执行。

## 3. 情境：决策的输入

每次决策针对一个明确的工作范围，而不是给整个项目强行指定唯一阶段。产品可以已上线，同时某项功能仍在设计、某个故障正在修复。

| 维度 | 需要表达的事实 |
| --- | --- |
| 工作范围 | 项目、当前任务、受影响模块及准备进行的操作 |
| 生命周期阶段 | 探索、设计、实现、验证、发布、运行维护、退出 |
| 场景 | 新建、新增、调整、修复、改善、重构、迁移、紧急恢复等，可组合 |
| 目标与约束 | 预期结果、范围限制、时间和成本约束、用户明确选择 |
| 当前资料 | 代码版本、产品文档、现有约定、依赖、候选资产和历史证据 |
| 风险与不确定性 | 影响范围、是否可逆、未知事项、证据是否充分 |
| 授权状态 | 已确认的能力、版本、用途、操作及范围；未确认项必须明确 |

生命周期与场景不是两套线性流程。例如“运行维护阶段的紧急恢复”可以直接进入诊断和恢复准备，而不重跑产品探索。

上下文中的关键事实必须附来源和时效或版本。AI 的推断与已确认事实分开表示；决定适用性所需的事实未知时，结果为待补充资料，而不是默认满足。

## 4. 钩子触发决策，不直接执行能力

钩子由可观察的工作事件引发，再结合情境决定是否采取行动。阶段标签本身不能直接授权操作。

| 钩子 | 触发事件 | 主要判断 |
| --- | --- | --- |
| 任务进入 | 接到新目标或恢复中断工作 | 识别范围、阶段、约束和所需资料 |
| 方案选择前 | 准备选择实现方案或工程方法 | 是否需要判断复用、适配或新建 |
| 关键操作前 | 准备修改外部状态、发布、迁移或其他高影响操作 | 适用实践、风险检查和授权是否满足 |
| 重要决策形成 | 产品承诺、长期约束或关键设计被确定或修改 | 是否更新已有产品文档 |
| 结果产生 | 实现、验证、复用或故障处理得到结果 | 是否修正判断、补充证据或提出沉淀候选 |
| 情境变化 | 目标、来源版本、风险、证据或授权范围变化 | 哪些旧判断失效，是否需要重新确认 |

这里只定义逻辑决策边界，不声称 Codex 已提供对所有操作的自动拦截。实施时，Supermind 必须在自己的调度入口接入这些边界；能够确定性检查的操作由项目命令执行检查。不经过该入口的手工操作不在自动保障范围内。

同一事件、规则版本和相关上下文未变化时，不重复检索、请求确认或执行。明确“重新评估”的请求或相关事实变化才重新判断。钩子之间存在因果链时保留关联，但不能因为写入一条决策记录就无限触发沉淀。

## 5. 统一决策结果

决策应说明：当前情境、触发原因、引用事实、适用规则及其版本、拟采取的行动、预期价值、成本、授权要求和完成标准。

允许的行动包括直接处理、补充资料、评估复用、建议适配、建议提取、更新文档、执行验证、请求确认、暂不处理和阻断。不能把“没有匹配实践”统一解释为“新建能力”。

记录粒度与风险相称：普通检查可以只在当前任务保留简短结果；长期产品决策、实际复用结果和重要阻断需要可追溯记录。不能为了证明每一步都经过决策而生成大量文档。

### 文档沉淀

产品承诺、重要约束或关键设计发生变化，且未来工作需要依赖它时，优先更新已有的权威文档。只影响局部实现而不改变长期认知时，不强制沉淀产品文档。

项目文档保存“这个产品需要记住什么”；可复用能力保存“其他情境也能采用什么”。更新项目文档不自动触发能力入库。

### 复用判断

在选择实现方案或工程方法前，如果已有成果可能减少成本或风险，就进入复用评估。先用触发条件和边界限定候选范围，再检索语义、评估契约和证据；相似度不能越过适用性约束。

同一规则集在准入和调用时使用一致的适用性语义。准入时描述的触发条件，不能在调用时变成仅供参考的标签。

## 6. 准入：决定什么以何种方式进入库

每个候选必须说明它解决的重复问题、预期使用方、通用边界、收益依据、提取及维护成本、实际载体和来源证据。没有必要性的内容可直接不收录。

准入判断有四种结果，不与现有生命周期枚举混为一谈：

| 结果 | 去向 |
| --- | --- |
| 不收录 | 说明理由，不制造长期资产 |
| 仅保留来源材料 | 按实际需要保留溯源内容，不进入可执行候选集合 |
| 提议抽象 | 展示提取目标、边界和成本，确认后才开展抽象工作 |
| 可登记候选能力 | 有实际资产、摘要、适用条件和钩子依据，按验证与抽象情况登记；不因此获准复用 |

来源材料需要独立识别，不能通过给清单文件填上“代码”类型或虚构收益来绕过现有准入检查。来源材料的存储接口和事件结构将在实施设计中明确，不能复用一个会将其当作可执行能力的接口。

### 三个独立维度

- 分类说明领域：代码、产品、设计、工程、工具、数据。
- 载体说明如何承载：原则文档、检查清单、操作流程、技能、脚本、代码模块等。选择满足用途的最轻量形式，不强制每项都做成技能。
- 钩子说明何时评估采用：一个能力可以挂接多个钩子，但每条绑定必须有明确理由和条件。

不能把新增的文档和流程载体硬塞成代码类型。现有模型尚未完整表达这些形式，实施时需要显式扩展和迁移。

### 每条钩子绑定的必要内容

钩子标识、适用阶段与场景、可判断的前置条件、排除条件、所需上下文、使用目的、预期结果，以及重新评估条件。

条件基于结构化事实表达，不允许能力条目携带任意可执行判断代码。复杂语义交由 AI 提供有依据的判断，不能靠字段断言自动视为成立。

没有明确触发情境的内容不能进入可调用能力集合；最多保留为有价值的来源材料。暂时不适用的能力可以保持休眠，不必为了调用次数而制造任务。

## 7. 调用、冲突和授权

先依据钩子和情境筛选，再做完整检索和资格判断。结果必须区分：没有适用能力、需要补充资料、检索或规则评估失败、存在待确认建议。

规则或资料不可用时，阻断依赖它的行动，不静默切换到另一套规则。没有命中可选实践并不代表故障，也不自动要求新建；顶层要求的必要检查不能因无匹配项而跳过。

匹配结果要转为当前任务的具体建议，指出资产、版本、用途、步骤和风险。用户确认后再执行；既往批准、默认选择、排名和能力库成员资格都不构成新一次授权。

多个实践冲突时，不机械叠加。先检查授权与硬约束，再判断与当前场景的具体适配程度和成本；无法消解的冲突请用户决定。操作范围或资产版本变化后，原确认不继续覆盖新范围。

执行结果记录实际发生的成本、收益证据及失败；无法测量的收益标为未知或估计，不冒充已经证实。失败、来源失效或边界变化时重新评估能力，而不是继续依赖历史推荐。

## 8. 在 Supermind 项目中落地

顶层指导和钩子定义属于 Supermind 项目及分发版本；具体可复用资产、绑定和证据属于能力记录。规则版本随决策结果保存，确保可以解释当时的判断。

复用已有的能力库、检索和事件机制，不再另建一套记忆系统。独立命令行工具承载结构校验、规则求值与决策记录；插件负责从 Codex 任务中整理情境并调用。不能只修改已安装技能来宣称项目完成升级。

实施顺序：

1. 先定义并接入软件开发项目准入，再定义情境、钩子、规则及决策的结构和版本约束。
2. 将准入和调用连接到同一决策机制，补齐载体与来源材料的表达。
3. 接入 Supermind 的任务、方案选择、操作前及结果处理入口。
4. 扩展能力展示，说明“为何收录、何时适用、何时不适用”，保持现有分类表格可读。
5. 完成兼容性处理、验证、远端发布，再从远端更新本地插件。

旧条目缺少触发绑定时，明确标记尚未评估，不自动补造条件或升级为可调用。新旧客户端的协议兼容性、派生索引重建及迁移需显式检查；不丢失既有来源、状态和证据。变更前必须预览并确认影响范围，不能借迁移重建用户能力库。

## 9. 首批验收情境

| 情境 | 预期决策 |
| --- | --- |
| 非软件项目中的文案、生活或一般事务请求 | 不进入 Supermind，无能力库和开发流程副作用 |
| 位于软件仓库但请求与开发无关 | 仍不进入，不能以目录或关键词代替关联依据 |
| 用户要求从零创建软件应用，尚无仓库 | 可依据明确的软件开发意图进入 |
| 用户只说“设计一下”，缺少项目和任务背景 | 先澄清，不初始化、不扫描 |
| 用户点名 Supermind 处理非软件任务 | 说明不适用，不因点名绕过准入 |
| 修改 README 的局部文案 | 按相关风险验证，不触发架构重设计或通用能力提取 |
| 修改公开接口契约 | 识别受影响消费者，更新必要契约文档和验证范围 |
| 新模块存在可能适用的既有实现 | 方案确定前判断复用，确认后才接入 |
| 发布后准备更新插件 | 检查远端发布来源、版本和安装结果 |
| 一次修复产生跨项目适用方法 | 提出来源与收益依据，确认后抽象，不自动入库 |
| 高相似度实践但前置条件不满足 | 不采用，不因排名而越过适用条件 |
| 无关任务命中相同关键词 | 不触发该实践或无意义确认 |
| 用户拒绝复用建议 | 不执行、不记录为复用尝试，讨论其他方案 |
| 已确认后来源版本或用途变化 | 使原决定失效，重新评估和确认 |
| 关键资料缺失或检索失败 | 明确区分待补充与故障，不当作空库 |
| 同一操作重入且相关情境未变 | 不重复检索、询问或执行 |

验收首先检查设计契约是否被落实，再检验实际成本收益；不能以“入库成功”或“检索命中”代替正确的情境决策。
