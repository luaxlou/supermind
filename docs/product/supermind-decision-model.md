# Supermind 开发哲学与设计边界

## 定位与目的

Supermind 是具有持续记忆、对软件项目结果负责的独立 Agent，当前通过插件挂载 Codex。它承接项目认识，组织能力推进工作，并根据实际结果和用户反馈调整行动。

意图、情境和对问题的理解会在人机协作中变化。Supermind 不把最初意图视为不变对象，也不以维护上下文连续性为终极职责；它提供与当前 AI 能力相匹配的协作范式，帮助应对变化。随着 AI 演进，范式可以修订、简化或退出，不要求 AI 自行证明和重写自己的规则。

人参与价值取舍和关键判断；AI 主动理解已有材料、组织证据和执行常规工作。不能把 AI 能承担的资料整理和流程维护转嫁给人，也不能以自动化为由替人决定价值与授权。

## 能力从实践中生长

“我们所有能力都是长出来的，并不是验证出来的。”从真实项目和当前需要出发，在使用、反馈和持续修正中形成能力，记忆承接积累。不要为能力成立预设验证阶段、迁移演练或审查关卡。用户明确无需验证时，不追加这类流程；未知、推测和实际结果如实区分。

沿用已有记忆、Git 提交及多端同步。重要认识更新原有相关材料；不另建 Agent 状态副本、工作状态机或交接协议。Codex 提供当前运行和工具执行环境，产品职责由 Supermind 指引表达。

## 软件生命周期作为共同坐标

生命周期预先定义为：构想与需求、设计、实现、验证、交付、运行维护、退出。它由 Supermind 项目版本维护，是共同坐标，不是阶段门禁、线性任务队列或所有场景的枚举。

同一项目中的不同工作可以处于不同阶段，也可以往返、跨越阶段。解释、询问、评估、探索、讨论、试验和复盘并非新增生命周期阶段，而是可按情境扩展的协作能力。

入口依据当前请求及已知背景判断是否与软件项目直接相关。没有仓库的新软件构想可以进入；位于代码目录中的无关生活事务不能进入。安装、更新和库管理按工具管理范围处理，不启动开发流程。不适用或关联未明时，不初始化能力库、扫描项目或创建开发文档。

## 核心决策与场景机制

核心大脑使用用户意图、项目事实、生命周期、具体场景和执行反馈，选择下一步动作。它负责何时解释、调查、检索、设计、实施、交付或结束；复用是其中一个动作。具体执行规则由分发技能中的[核心决策](../../plugins/supermind/skills/supermind/references/core-decision.md)维护，场景与触发条件由[生命周期与场景](../../plugins/supermind/skills/supermind/references/scenarios.md)维护。

生命周期是共同坐标，场景规定行动的进入条件与时点。后端选型、本地运行方式、单机部署方式等场景在作出依赖能力的实现决定前必须查询相应需求。已有有效结果继续使用，新的独立需求重新检索；单纯讨论、局部文案修改或日常使用不机械触发。

AI 主动读取必要材料并承担常规工作，用户参与价值和关键取舍。结果可以是一份解释、一次讨论或一个实际实现，不强制完成固定流程。收到用户修正或执行反馈时重新判断，已有授权持续有效。

[核心决策机制设计图](2026-09-07-core-decision-mechanism-design.md)解释总体关系与实际调用链；它不构成第二套运行规则，也不取代技能入口的实际引用。

## 预置高回报的核心复用范式

顶层保持开放，不妨碍预置常见且价值较高的能力。

| 核心范式 | 介入依据 | 提供的价值 |
| --- | --- | --- |
| 响应复用要求 | 用户明确要求查找或采用已有成果 | 找到候选、解释边界，经人确认后使用 |
| 评估复用 | 稳定模块或工程方法可能已有成果可用 | 比较复用、适配、提取和新建的收益与成本 |
| 发现可复用能力 | 开发、试验或复盘产生可能跨情境受益的成果 | 识别必要性和抽象空间，建议沉淀或不收录 |

范式的具体材料和入口由分发包中的[生命周期与核心范式](../../plugins/supermind/skills/supermind/references/actions.md)维护。这里不建立第二套场景状态机或规则求值系统。

## 价值、抽象与沉淀

代码和工程实践都可能复用，但不能仅因工作完成就收录。候选需要说明：解决什么重复问题、何时适用及不适用、使用需要什么材料、通用边界、真实载体和来源、验证依据、预期收益以及提取接入维护成本。未知或估计的收益不能冒充实测结果。

具体业务实现首先是来源材料。更换名称、摘要或状态字段不等于抽象；代码资产必须有实际代码来源。工程实践可采用原则、清单、模板或方法等合适形式，不必强制包装成技能。

经人确认后才登记候选；每次具体复用仍需确认能力、用途和改动范围。入库、验证和过去批准不构成本次授权。分类、抽象状态、验证结果与授权是不同维度。

未来工作需要某项认知时，优先更新现有项目材料。项目文档回答这个项目需要知道什么，通用资产回答其他情境可以采用什么。没有长期价值时，不制造文档或能力条目。

## 复用内容与呈现

能力定位依据官方项目文档和实际职责。入库前提供简洁名称、实际用途、官方项目与接入入口、分类、完整触发情境及确认后的接入方式。已有独立框架或工具直接收录其本身，不包装成从某次项目开发中提取的新能力；当前机器上的路径和一次运行结果不能替代可供其他项目获取的正式来源。具体规则统一维护在技能的沉淀指导中。

分类按复用价值，载体按真实资产，两者分别判断。代码复用与工程化工具分别触发，不因曾在同一项目使用就强制绑定。例如，新项目需要后端时优先考虑 Nova Go 的代码与最佳实践；Nova CLI 属于应用管理工程能力，项目需要本地生命周期或单机发布、日志管理时独立考虑，不以 Go 后端为前提。由 AI 在实际接入时判断当前能力与项目的兼容性；发现重大冲突时再说明和处理，不固定来源版本，也不把版本确认作为独立环节。

总览和分类目录统一使用“名称、说明”两列；名称为简洁的“中文名（英文名）”，不附加宣传性定语、不另列英文标识。说明使用较小字号。不显示能力状态列、状态分组及生命周期管理说明。详细卡片必须保留可点击的官方项目入口；省略经验来源项目的强调，不等于省略复用资产的地址。CLI 目录与 GitHub 目录复用同一呈现逻辑。

用户对定位或触发提出异议时，重新依据原始资料形成具体修订内容，按用户要求确认；明确授权直接改造时继续执行。关于复用方法的反馈必须同时落实到 Supermind 源码、技能指导和实际输出，不能只修改一个库条目。验收关注另一个项目能否正确理解并获取、接入能力；同步成功不代表复用内容正确。

## 技能与工具的关系

Superpowers 是可选的生产力能力来源，与其他插件和项目工具一样按适用性选择，不定义 Supermind 的固定流程。先判断方法是否适合当前情境；选择后遵守适用的技能要求。新的用户要求改变范围时重新判断，而不是要求用户适应已经过时的方法。

灵活的协作范式不取代授权、安全和工具协议。需要完整能力库检索时，失败就是故障，不能解释为空库或改用新建绕过。无需用库的解释与讨论，不被无关的初始化前置条件阻断；这是范围划分，不是降级策略。

## 本版实现范围

本版通过插件入口、核心决策指引、生命周期与场景指引以及能力调用指引，落实场景识别、动作选择、明确时点的检索和结果反馈。它们属于随插件分发的 AI 指导，不是运行时对所有 Agent 行为的自动拦截，也不保证任何模型都不会误判。

能力库继续使用已有独立 Python CLI、完整检索、质量评估、人工确认指导和事件同步，不新增存储体系，不修改用户数据。CLI 的基础校验不证明语义通用性，也不代替人确认。

场景上下文写入现有查询需求的 intent 和 contract，继续调用 search 或 begin-design。场景识别与时点要求由技能执行，CLI 处理被调用边界内的检索；没有新增宿主全局监听器。载体枚举仍未涵盖任意原则文档或流程。遇到不支持的资产形式，明确报告接口缺口，不伪装类型、补造证据或替换存储。

以后扩展应来自实际收益和使用反馈，并与 AI 能力相匹配；不是先穷举场景、建设大而全决策引擎。源码修改、发布与更新已安装插件分别按用户授权推进；本轮只完成源码迭代，不发布、不更新本地插件。
