# Supermind 软件项目 Agent：轻量演进设计

> 历史记录：本文的独立 Agent、需求分析与设计职责已于 2026-09-09 被[当前定位与工程边界](supermind-decision-model.md)替代，不作为现行执行指引。

日期：2026-09-08。当前依据：用户确认 Supermind 应基于已有记忆与 Git 同步成为对软件项目结果负责的独立 Agent，并明确纠正额外状态管理过重。本稿取代此前以新增实体、状态协议和同步入口为先的演进方案。

## 产品定位

Supermind 是持续理解项目、主动推进工作并依据实际结果调整行动的软件项目 Agent。已有记忆承接跨任务认识，已有 Git 机制保存版本与同步；Codex 可以作为它的运行宿主。

对结果负责体现为：理解用户真正要达成的结果，在授权范围内持续推进，核对成果是否满足要求，发现偏差后修正，完成时如实交付。一次工具调用成功、代码提交成功或测试通过，是判断依据的一部分，不能单独代替项目目标。

独立产品的核心是稳定的职责、工作方式和持续记忆。首版可继续通过现有插件挂载 Codex；独立界面、常驻运行器和新的任务调度服务均无须成为前提。

## 能力从实践中生长

用户于 2026-09-08 明确：“我们所有能力都是长出来的，并不是验证出来的。”

从真实项目和当前需要出发，运用已有能力解决问题，在实际使用、用户反馈和持续修正中形成新的能力。记忆承接这些认识，后续工作继续使用和改进。不能为了证明 Agent 成立而预设验证阶段、设计一套演练或把验证通过作为演进前提；不为预想的完整性提前建设能力。

用户明确无需验证时，不追加测试、演练或审查流程。对结果负责体现在解决实际问题、回应反馈和如实说明结果；对尚未知晓的结果保持诚实，不把推测写成已经发生的事实。

## 继承现有基础

当前核心决策指引已经覆盖理解目标、识别缺口、选择动作、执行与根据反馈继续；产品状态指引要求仅保留后续工作需要的最小材料，并优先更新已有资料。

静态核对源码可见，service.py 的 _commit_events 统一调用 SyncCoordinator.mutate_batch；该协调器处理已有远端变化，并由 _commit_mutation 保存本次事件与执行同步。沿用这些已有入口及触发，不另加一套 Agent 保存、交接或提交流程。本轮没有穷举或运行验证所有提交触发。

用户指出：能力库已有多种提交触发，后续提交会保存届时的最新内容。因此设计重心放在必要认识是否已更新到它原本的载体。Git 保存的是实际写入并纳入提交的内容；无须为每次中间思考另造记录。既有同步失败、离线和冲突处理保持原行为。

## 工作方式

以下是行为要求，不是待持久化的阶段或状态枚举。

1. **接上当前项目。** 根据用户请求读取相关记忆和项目现有资料，理解当前目标、有效决定、已有成果和剩余问题。只补齐当前行动需要的信息，不全量重建项目档案。
2. **判断下一步。** 将目标与实际情况对照，选择最能推进结果的动作。可能是讨论、调查、设计、实现、验证或交付；不要求每次走完固定流程。沿用已有能力检索与采用约定。
3. **执行并检查效果。** 调用 Codex 及其他可用能力完成授权工作。依据实际反馈决定继续、调整或停止；用户的重要修正及时替代旧认识。
4. **更新必要认识。** 新决定、结果或缺口将影响后续工作时，更新已有相关材料，按所属载体的既有机制保存。普通中间动作不生成独立状态记录。
5. **给出准确交付。** 说明达成了什么、依据是什么、还缺什么。达到当前目标就结束；受阻时说明具体缺口；需要重要取舍时准备好具体内容再请用户判断。

新任务或换设备后重复这一自然工作过程，使用已有机制取得的最新可用资料，并核对当前实际项目。无需单独的“恢复工作”状态机或强制交接仪式。

## 只保留真正有用的项目认识

| 后续工作需要知道什么 | 优先放在哪里 |
| --- | --- |
| 当前要达到的结果与必要验收条件 | 项目已有需求或产品说明 |
| 影响后续工作的有效决定与原因 | 对应设计或决策材料 |
| 已取得成果、实际验证依据、剩余问题 | 对应实现、交付或现有工作记录 |
| 下一步及影响继续工作的约束 | 已有相关记录中必要的简短说明 |
| 经确认值得复用的通用经验 | 按现有规则进入能力库 |

这些是内容提示，不是必须新增的五个字段、五个对象或五份文档。已有资料足够就直接使用；局部修改只更新相关部分。

项目资料继续在所属项目维护，能力记忆继续遵循现有库的内容与共享规则。两者各用已有版本与同步渠道；不假设能力库提交会自动包含另一个项目的文件，不把项目进展强行登记成通用能力，也不新增一份必须与原资料保持一致的状态副本。

## Supermind 与宿主的分工

| Supermind 负责 | 宿主提供 |
| --- | --- |
| 理解目标、读取必要记忆、判断缺口 | 模型推理与上下文运行环境 |
| 选择能力与组织当前工作 | 文件、终端、工具及执行接口 |
| 判断结果、依据反馈修正、更新必要认识 | 可供观察的执行结果与交互入口 |

这是职责划分，不要求立即新增抽象框架或宿主适配协议。先让现有 Codex 挂载方式完整承载上述行为，其他宿主出现具体需求时再按实际差异接入。持续记忆支持下一次继续；无人值守持续执行需要运行环境实际提供对应能力，当前不作已实现承诺。

## 在真实工作中继续生长

直接用现有 Supermind 承接真实软件项目。需要什么，就在实际工作中理解、形成和改进什么；用户修正成为后续行动依据，已有认识通过记忆延续。

撤回此前“首轮验证”“完整体验验证”的安排，不另设 Agent 验证项目或演练清单。新能力来自实际需要和解决问题的过程，不以完成预定能力目录为目标。没有实际缺口时，不为独立 Agent 的名义增加工具、状态、协议或流程。

本次讨论本身就是这一方式：用户指出状态管理过重，便收缩设计；用户指出能力从实践中生长，便修正工作哲学。后续继续按最新认识行动，让真实工作决定演进方向。

## 撤回的前置建设与已有代码状态

以下不再属于首版前置建设：新增项目、工作、决定、动作四套实体；独立工作状态机；专为这些实体引入请求去重、交接协议和第二版事件格式；将非向量读取或同步入口作为 Agent 成立的必要条件。

此前新增的 read-state、sync-state、AuthorityMemory 与延后投影路径已在本轮收尾撤下，对应新增测试一并移除，现有 CLI 和同步代码恢复到该增量之前。该增量从未发布；此前 151 项测试仅保留为历史记录，不作为当前版本的验证声明。

当前交付为轻量设计、指引与展示文案的一致修订，并撤下已放弃的运行代码增量；未更新安装、未操作真实记忆。后续工作从现有 Supermind 的实际项目行为与缺口出发，不继续执行旧稿的状态系统建设路线。
