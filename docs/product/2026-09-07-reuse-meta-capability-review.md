# 复用元能力失效审视：从经验整理到可复用交付

> 历史评审记录：需求分析与设计方法及其调用规则已于 2026-09-09 撤回，当前范围见[Supermind 工程边界](supermind-decision-model.md)。

日期：2026-09-07。范围：线框设计经验沉淀、Supermind 的相关技能规则和实际入库工具。前文保留最初审视时的状态；后续升级及本次内容审查结果见文末。本文是本项目的审查记录，不登记为另一条共享能力。

## 结论

直接原因是执行者没有完成已被要求的抽象审查：把会话经验整理、增加模板和入库成功当成了任务完成。规则已经存在，不能将责任推给缺少提示词。机制上的薄弱处在于：来源记录与复用资产共用入库入口，语义审查依赖执行者判断，而工具返回成功缺少与用户目标对应的完成判定。

这次问题发生在“经验整理 → 抽象审查 → 入库交付”，不是已发生跨项目复用事故。实际采用入口仍会拒绝抽象未完成或缺少当前验证的条目；该防线存在，不表示此次沉淀任务合格。

## 本次实际发生了什么

1. 用户要求将已认可的设计实践沉淀为工程经验，复用约束要求先抽象。
2. 执行者读取了技能和原会话，初始化、健康检查和相关检索均完成。
3. 执行者创建了包含通用方法和模板的文档，但把原会话链接、本机项目文件、案例复盘和估计评分也放进复用正文；源资产仅指向本机新草稿。
4. 执行者给条目标记待抽象，调用 `complete-implementation`，得到入库、同步成功。状态没有虚报已抽象，但交付仍把未完成用户要求的结果说成已沉淀完成。
5. 执行者读取了生成后的能力卡，却只确认了内容存在，没有按“另一个项目能否独立理解、取得并采用”的标准否决自己的产物。
6. 用户指出问题后，正文改为独立方法和模板，补齐输入输出、可配置边界及完成依据；取得入口改为共享能力卡，原始证据保留在审计历史中。

## 已排除与仍需谨慎的判断

- 不是没有读取规则：此前已读取要求真实通用边界和审查生成卡的规则。
- 不是检索或同步失败：相关操作有完成结果。
- 不是安装版本不匹配：已核对当前安装的 0.5.0 插件所锁定的 0.3.13 工具 wheel 哈希；其 quality、service、workflow、types、lifecycle、decision 模块与所审阅源码逐字节一致。
- 不能说整个复用约束都没有生效：[decision.py](../../capability-memory/src/supermind_memory/decision.py) 的采用资格判断仍检查抽象、验证、契约、价值与来源。此次没有完成一次真实的跨项目采用。
- 已有测试包括“正分数不证明必要性”及审计仍需人工判断；检查过的入库与质量测试未证明执行者会正确完成工程经验抽象。此处没有声称穷尽所有测试或重新运行全套测试。
- 删除路径和改成远程链接只解决部分可移植性问题；还必须检查隐含业务假设与采用步骤的完整性。

## 改进顺序与验收依据

先把语义完成标准落实到当前工作，再决定工具如何辅助，避免再增加一个只能由执行者自行勾选的状态。

| 优先级 | 建议 | 如何判断有效 | 当前状态 |
| --- | --- | --- | --- |
| P0 | 修正本条正文与取得入口 | 不读取原项目、原会话或本机文件，也能明确输入、输出、步骤、配置项和完成依据；远程正文与本地拟交付内容一致 | 已修正并同步；尚无独立第二项目实践验证 |
| P0 | 明确工程经验独立性与来源追溯边界 | 技能入口与沉淀指引一致；不能用 pending、模板载体或同步成功来替代抽象成果 | 仓库规则已修改，未发布安装更新 |
| P1 | 区分来源观察的登记和抽象成果的交付 | 同样的来源笔记可以作为观察保存，但不得因接口成功自动变成“抽象完成” | 待工具设计；不改变合法观察的价值 |
| P1 | 给抽象审查提供与产物绑定的证据 | 记录审查对象的内容版本、输入输出、可配置边界、移除的依赖及尚存限制；产物变更后旧判断不能自动沿用 | 待设计；不接受仅一个 `approved: true` |
| P1 | 给机械检查和语义审查划清职责 | 路径依赖、必需材料不可得等可检测问题明确提示；通用性由具体内容评审，不靠关键词扫描宣布通过 | 待设计与有针对性的回归用例 |
| P2 | 修正共享资产入口标签 | 工程文档显示“模板文档”等准确标签，外部库仍显示真实官方项目 | 已定位，未修改或发布运行工具 |

下一轮验证元能力应围绕实际产物，而非检查是否调用了某个工具。可使用以下对照情境评审：

- 只给复用者通用文档和其自己的项目材料，分别套用到内容发布审批与设备维护管理；检查是否需要原案例才能补齐理解。这是拟议的独立性检查，不是已发生的两次真实复用。
- 含本机必要引用、换名但保留行业状态机、只有空白模板的产物应不能被宣称为抽象成果。
- 有合法外部依赖及真实获取入口的能力应被允许；不把“有任何链接”一概视为未抽象。
- 来源观察可以保留，状态不得自动升级；有用的通用方法也不能因未完成第二项目实践而虚构验证证据。
- 每次真实采用仍遵守用户授权边界，结果回写实际成本和收益。此次是纠正沉淀，不伪造一次复用记录。

当前能确认的是条目正文和仓库指导已经纠正，不能因此宣布复用元能力整体已修复。工具层改进、发布以及新任务中的行为验证要分别取得证据。

## 后续升级：敏感历史与再次污染防护

本轮新增 `privacy-audit` 和 `purge-sensitive`，在保留干净资产的同时重建历史基线。写入约束覆盖正文、来源、证据、审计和元数据；自动发现只返回本地观察，不能通过来源注册表重新同步原始项目。模板来源的标签改为“模板文档”。具体执行、失败保护与服务端清理边界见[敏感历史清理说明](capability-memory-purge.md)。

这些检查解决可识别的本机/会话来源泄漏，并不证明所有业务耦合已经消除。元能力的语义审查仍须针对可移植内容、输入输出、配置差异和具体采用依据执行；不能再以隐私扫描通过替代抽象完成。

## 0.6.1：把抽象完成条件接到行动入口

本轮修改技能入口、核心决策、场景入口和沉淀指引，统一指向[抽象审查](../../plugins/supermind/skills/supermind/references/abstraction-review.md)。审查对象包括能力卡、技能和模板；候选登记不再被解释为用户要求抽象成果时的替代完成条件。共享的“按风险与证据决定验证”技能也移除了原任务标识和单项目测试统计，仅保留通用方法及成熟度限制。

没有添加自动宣称语义通过的新状态。独立 CLI 仍为 0.3.14，工具登记成功仍只证明登记。此次修复是代理的行动规则和实际产物审查，不宣称机器能识别所有业务耦合。

### 本次线框方法内容审查

审查正文：[线框图驱动的设计基线协作](../archive/requirements-and-design/wireframe-design-baseline.md)，文件 SHA-256：`e0d3510f6fcbd1c93deefbd1875038983e80daa407b184acc8d33d32b40c5625`。使用独立 CLI 读取共享能力卡，对照正文：方法、模板、可配置边界、完成依据及收益限制一致；生成器对部分强调符号转义，不影响步骤含义。没有重新登记、增加来源记录或把本报告同步进能力库。

以下是本次审查者完成的纸面推演。输入均为虚构示例，只用于检验正文独立性；没有修改真实目标项目，没有实际复用、用户确认或收益测量。

#### 推演一：内容发布审批

采用方输入：编辑提交内容，审核员可以退回或批准；批准不等于发布。用户仅要求设计审核页，已有左侧导航和待审列表，需保留结构。

依照“先明确职责与生命周期”，区分内容版本、审核决定和发布状态。依据“把职责落到文字线框图”，得到草稿 `RV-01`：

```text
审核页 / 内容版本                         [退回] [批准]
A. 标题、提交人、当前版本、审核状态
B. 内容预览                 C. 变更说明和审核记录
```

由输入提供“批准不发布”的规则；方法只要求状态归属清楚，没有发明发布流程。退回需理由，批准后展示审核结果；发布状态归属另一个阶段。版本在操作前变化时提示重新查看，权限不足时不给出可执行批准操作。返回列表保留原筛选和选中项。

本轮输出是线框、区域说明、操作结果和待决事项。批准是否需要二次确认不是已知事实，明确待定。由于只授权设计，不实现、不标冻结。这些结果分别对应正文的职责、交互路径、上下文、异常状态和授权边界；不需要原项目资料。

#### 推演二：设备维护，改变布局和状态假设

采用方输入：维修人员使用窄屏现场填写检修单；设备可能停机，但检修单完成不直接代表设备可运行；离线提交策略尚未确定。

依据可配置边界，将模板两栏改为单列草稿 `MT-01`：设备身份与状态 → 检修步骤与填写结果 → 附件 → 提交检修记录。业务字段由采用方模型提供，不从方法中推定。设备状态与检修单状态分别标明；提交只更新检修单的已知结果。

离线策略作为阻断提交行为设计的待决项；不能把未知策略画成“已成功上传”。返回时是否保存未提交填写内容也列为待决，不沿用审批页的已知行为。此变化无需改写方法，只调整角色、状态归属、布局、数据和确认项。输出足以继续讨论，尚不满足最终设计完成条件。

#### 拒绝和边界情境

| 输入或候选产物 | 本次判断及具体原因 |
| --- | --- |
| 只改按钮文案，已有明确行为 | 裁剪掉全站线框与重新确认流程；正文“何时值得使用”明确排除低影响修改 |
| 保留完整标题但只有空白表格 | 不能交付：缺少从材料到设计判断的步骤，采用者无法知道如何填以及如何判断完成 |
| 删除项目名，却规定所有模块必须采用固定三个状态 | 不能交付为通用方法：审批和检修输入中的状态归属不同，候选把原业务状态机固化成通用规则 |
| 要求打开原作者本机的参考稿才能理解编号 | 不能交付：采用的必要材料不可得，独立性失败，即使字段齐全且收益估计为正 |
| 将上述候选改标 `pending` 后注册成功 | 仍未完成用户要求：保存状态不补齐方法，必须继续修正正文 |
| 自包含方法链接真实、可取得的通用规范 | 不因有链接而拒绝；检查规范是否必要、可得及边界是否说明 |
| 工具要求独立来源与验证证据，但只有纸面推演 | 不复制原项目凑字段，不把推演标成运行验证，不自动提升库内状态 |

结果：现有线框正文在两个推演中能形成具体设计草稿并暴露待决事项，不依赖原案例；暂不需要改写正文。原案例的定性认可仍不能证明两个虚构项目中的实际收益。此次是同一执行者的内容审查，不是独立代理评测，也不能保证未来每次执行都会遵守规则。

后续真实任务的验收观察点：是否先交付可操作方法、是否在入库前完成具体迁移推演、是否把原始材料留在来源环境、是否正确区分纸面推演和真实采用。出现违反时直接依据产物追查行动入口，不能仅补一句提示或再报一次扫描通过。

## 需求基线方法：入库前内容审查

审查对象：[需求基线协作与变更追踪](../archive/requirements-and-design/requirements-baseline.md)。该方法与 UI 基线职责不同；完整检索返回的现有线框方法不覆盖需求规则和验收基线，没有合格的等价条目，因此新增独立工程方法。以下输入及结果均为虚构的纸面推演，不是实际项目采用。

- **退货受理场景**：采用方给定“已签收订单的买家可申请退货，本期不处理退款，订单资格由既有规则判定”。产出 `REQ-01`：输入订单与原因；资格不符拒绝并说明，资格符合创建退货申请；不得直接改变退款状态。验收包含未授权买家被拒、有效申请创建、退款状态不变。退款明确列为范围外；具体时限未知，作为资格规则依赖，不由审查者编造。对应受理接口、申请 UI 和验收用例；仅形成草稿，未冒充用户确认。
- **无 UI 的批量导入场景**：采用方给定“服务接收一批记录，校验后写入；失败是否允许部分成功尚未决定”。产出 `REQ-02`：输入格式、校验错误输出和写入结果需明确；事务范围列为阻断写入语义设计的待决项。可以继续设计输入解析，不能擅自承诺整批回滚或部分成功。对应接口、数据规则和验收，无需创建页面。
- **改变假设**：若有效决定从“整批成功或失败”改为“逐条处理”，保留需求编号，记录原规则到新规则，影响事务设计、结果接口和失败用例；只有旧解析证据仍适用，原整批原子性验收不能沿用。正文的变更与证据边界支持这一判断。
- **拒绝情境**：只有一张通过评审的效果图不能宣称需求基线已确认；只改颜色不要求重新建立需求；已有代码不自动成为业务承诺；纸面推演不形成真实复用记录。上述判断均能从方法正文获得，不需要原始出处。

完成判断：正文可产生可追踪需求与验收，并在缺少决定时给出明确的可继续范围。迁移不预设行业状态机、UI 或审批方式。收益仍为定性预期；入库工具所需数值仅作相对价值假设，不解释为工时或测量结果。库内保留候选成熟度，不伪造运行验证或另建私有来源记录以提升状态。

## UI 基线命名及依赖关系修正

现行名称改为“以线框图作为 UI 设计基线”，原“驱动”措辞过度扩大了线框的职责。需求基线是其输入前提；线框承接界面结构、信息和交互，并作为 UI 深化的比较依据。高回报来自用户的定性实践反馈，未计算 ROI 或测得节省工时。

本次回看受影响的推演：审批和维护页面必须先有当前范围的需求依据；假定该范围需求已确认，页面可据此承接并追溯。原推演中缺失的业务决定仍不得靠线框补齐，受影响区域只能保留探索草稿。纯视觉修改不重开需求，批准权限或设备状态含义变化必须回到需求修订。没有 UI 的导入需求继续只映射接口和数据规则。两篇正文的职责与依赖一致，无需访问原案例。

前述 UI 内容摘要对应修正前版本，不再覆盖现行文字；本轮内容审查以此次提交的两篇正文及入库的内容摘要为准。修正只影响命名、需求前提和相关追溯要求，不把纸面推演升级为实际项目验证。

## 设计阶段语境与触发范围修正

两项方法的分组改为“设计阶段”。“设计协作与基线管理”错误地把阶段内应完成的动作当成独立触发域。现行规则在实际进入设计阶段时加载两份完整方法和目标项目现行基线，在整个阶段持续使用；需求变化更新项目语境，换页面或继续讨论不重新查库。

对修订正文做了以下执行情境推演：首次进入且未加载时取得两份正文；第二个页面直接使用现有语境；调整权限时更新需求和受影响的 UI，不重新搜索方法；无 UI 的接口设计仍承接需求并标注 UI 不适用；上下文丢失时只补读丢失正文；独立后端框架选型仍进行自己的能力检索。均能从现行阶段指引和两份正文得到一致行为，不需要新增阶段服务或私有来源记录。

这里验证的是技能指引及正文的纸面行为一致性，没有运行真实多轮设计任务，也没有为 CLI 声称不存在的自动阶段监听能力。后续实际任务应观察“只在入口加载、阶段内持续使用”是否得到执行。

## Nova CLI 定位和采用边界修正

定位改为“小型个人应用的运行生命周期管理”，范围包含构建、发布、运行、停止、重启、状态和日志，不涵盖需求和设计等完整项目生命周期。官方 README 用于核对功能和入口；“只用于小型个人应用、不用于生产级应用”是本能力库明确的采用边界，不冒称来自一次安全审计。

同步修正能力正文、摘要、约束、分组、使用示例和两个选型入口。边界推演：非生产的个人小应用可以进一步评估；个人维护的线上生产服务仍排除；单台服务器不是安全充分条件；要求完整需求到交付管理时不把 Nova CLI 当成覆盖方案；已装客户端不自动构成接管授权。没有执行实际应用接管或安全测试。

## 工程能力按场景分类与触发

本次修正替代前述“设计阶段语境与触发范围修正”的阶段绑定结论。生命周期是工作背景，具体场景决定钩子；设计活动可贯穿项目生命周期。工程目录采用简洁分类名：需求、界面设计、基线管理、应用运行。具体触发场景留在能力说明中，分类名不枚举所有动作。一个能力只维护一份正文，在场景中说明常见生命周期位置，不按阶段复制。Nova CLI 仅调整目录和检索标签，保留官方入口、用途及非生产限制。

审查对象为三份工程方法的场景触发正文，以及入口、核心决策与基线场景语境。方法本体保留在能力库，Supermind 仅修改调用路由，不重新内嵌基线管理方法。

- **独立推演**：运行中的预约系统出现取消口径冲突，触发需求澄清；若据此修改界面，再触发 UI 场景；跨文档和实现有差异时组合一致性对齐。项目无需被标记为设计阶段，也不自动授权编码。
- **变化条件**：验收发现交互偏差，可使用现行需求和 UI 方法，不必重新加载需求方法。无 UI 的退役数据保留方案只澄清需求和相关一致性，不引入 UI。
- **拒绝情境**：仅说“进入设计阶段”、更换任务或日常启动应用，不触发固定方法加载、重查能力或重新引入工具；正常工作沿用已有依据。
- **依据边界**：读取正文、提出采用、实际复用分别判断，库中成熟度与采用授权不因场景命中而提升。纸面推演没有产生真实运行或采用证据。
