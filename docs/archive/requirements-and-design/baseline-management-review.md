## 项目一致性核心目标推演

预约系统需求规定“取消后释放名额”，设计描述释放，代码仅更新预约状态，验收只检查状态。依正文对应表记录需求到设计、实现和证据的链路，识别名额处理与验收缺口；当前仅授权设计时补齐相关设计与验收条件，将实现差异留为后续工作，不立即编码，也不将需求改成代码现状。若共享标准允许不同预约类型采用不同释放时机，则明确各范围的依据，不强求相同行为。这个产出体现项目一致性管理，编号与归档仅为支撑。未受影响模块不重新扫描或验证。

设备预约系统已确认列表交互，取消规则未定；采用方要求本轮功能需求设计完成后统一开发，已有设计索引。依方法产出：`DES-BOOKING-LIST V1.0`，确认范围仅为列表交互，基线状态已确认，取消规则列为未决；索引链接固定版本，设计继续，实现未开始、未验证；下一步设计取消规则，开发条件为本轮设计完成且有效授权涵盖实施。建立这条基线后可结束当前规划。业务事实和启动条件由采用方提供，记录结构及交接步骤来自正文。

## 改变假设

改为没有界面的消息导出接口，采用方已确认契约并授权立即实现，只有一份版本化文档。方法产出接口基线，无 UI 字段，不创建多余索引；前提齐备即可实施，不强制等待全产品设计。后续输出字段改名时先形成修订草稿，记录调用方影响，确认后保存新版本并更新现行入口，旧版仍可恢复。编号、载体和开发节奏均在声明的配置边界内。

## 历史归档补充推演

接口 V2 在新调用方生效，但旧调用方仍使用 V1。按方法保留两个明确适用范围的现行入口；V1 退出使用后，将正文、依赖版本、确认依据与变更记录归档，历史索引登记日期、原因及 V2 替代关系。使用 V1 的历史验收任务仍定位 V1 快照。需要恢复旧字段时形成 V3 修订并确认，不将 V1 直接改回现行。首次建立无旧版时不制造归档；归档不触发删除。此推演支持归档规则的内容完整性，未对实际仓库执行归档或验证链接。

## 拒绝情境及缺口处理

- 一张未经确认的效果图只能记录为草稿，不能靠编号宣称基线成立。
- 两份相互矛盾的现行文档须先明确有效决定，不能依据修改时间自动选择。
- 只有“最新版”链接无法恢复旧内容，正文要求固定修订或保留版本。
- 基线已建立但条件未满足，不能因为旧计划含开发步骤启动实现；条件满足但无实施授权也不能启动。
- 一次性文案修改可沿用现有约定，不强制完整流程。

推演未依赖原项目、会话或业务标识。正文已补齐版本恢复、组合基线成员版本和条件与授权的区别。限制是纸面内容审查，不能记录真实采用成功、节省工时或运行验证通过。

## 对齐状态补充审查

虚构仓储项目要求“出库后同步可用库存”。设计已明确扣减规则并有对照依据，标设计已对齐；实现因等待本轮设计收束而暂缓，记录恢复条件、承接任务及关闭条件；验收未核对，下一步补充相关用例。概览明确当前可推进验收设计，不能因设计已对齐宣称项目全部对齐，也不能自动启动实现。若外部库存接口尚无契约，实现记受阻并列解除动作，而非泛称未完成。

改变条件：仅修订说明且版本不变，发现原设计遗漏失败补偿，受影响项转为待对齐，其他已覆盖项保留证据；更新状态不产生历史快照。没有任何依据的项目初始化为未核对；无界面服务不强行增加 UI 对齐项。归档旧版保留当时未完成状态，新版重新判断继承范围。推演只检查方法可操作性，不代表上述虚构项目真实验证。
