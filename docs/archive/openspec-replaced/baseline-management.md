# 基线管理

将需求基线、UX 基线和 UI 基线作为三种独立维护的工程依据。每种基线有自己的正文入口、条目编号、版本与修订记录、确认依据、未决项和对齐状态；通过引用建立关联，不合并成一份泛称“设计基线”的正文，也不共用一个总版本号。

本方法维护已经明确的成果及其变化。需求分析、UX 方案与 UI 设计由上游完成；维护基线不授权生成新方案、推定业务规则或立即实施。

## 何时采用与所需输入

收到上游确认成果、需要修订某种基线、处理跨基线差异、对照实施或交接任务时采用。已有有效依据直接沿用，普通任务续接不重建全部基线。

输入包括当前范围的已确认成果、有效决定与授权、现有文档和版本约定、相关代码及验收事实。只有影响当前工作的信息才需补齐。未知内容保留为未决项，不能从代码现状或文件时间推断已获确认。

输出是三种各自可定位、修订和追溯的基线，以及必要的引用和对齐记录。沿用项目既有文档系统；采用方可配置文件路径、编号、版本格式、维护人和归档方式。没有交互或界面的范围可分别标记 UX、UI 不适用，不制造空文档；应有但尚未提供的内容标记缺失，不能冒充不适用。

## 三种基线的职责

### 需求基线

记录要达成的结果：用户与业务目标、范围及排除项、业务对象和规则、权限与业务状态含义、输入输出边界、验收条件。验收条件涵盖有 UI 和无 UI 的需求。

需求条目使用稳定编号，例如 REQ-001。每项保留来源、确认依据与可观察的验收结果。需求基线不以线框、页面布局或颜色替代业务规则；其他基线引用需求编号，不各自复制一套规则。

需求规则发生实质变化时，以新的上游决定修订需求基线，记录受影响的 UX、UI、接口实现和验收项。仅调整排版或交互表达且未改变业务承诺时，不据此改写需求基线。

### UX 基线

记录用户如何完成任务：任务与场景、信息结构、入口及导航、操作路径、交互规则、成功与失败路径、等待反馈、恢复与返回行为。它引用需求基线中的目标、权限和业务规则，记录这些规则的交互表达。

UX 条目使用独立编号，例如 UX-001，并注明对应的需求条目及版本。操作产生什么效果、确认或撤销如何发生、出错如何恢复属于 UX；颜色、字号、间距和具体样式属于 UI。业务状态含义归需求，界面在该状态下允许的交互和反馈归 UX。

UX 改动单独记录确认与版本，不因交互变化自动修改需求。若暴露未定业务规则，先交回上游澄清；仅在新决定成立后更新相关基线，不能让 UX 文档悄悄改变需求承诺。

### UI 基线

记录已确认界面的具体呈现：页面与区域布局、组件及变体、视觉层级、字体、颜色、间距、图标、响应式规则及各交互状态的视觉表达。设计稿、视觉规范、组件规范或代码化样式资产都可作为成员，但需指明对应版本和现行入口。

UI 条目使用独立编号，例如 UI-001，并引用相关 UX 条目及版本，必要时直接引用需求条目。视觉参考只证明风格参考，不能替代已确认的 UI 基线。线框中包含的操作规则归 UX、布局约定归 UI；复合设计文件可按页面、节点或区域引用，同一规则只维护一个权威入口。

UI 可在不改变任务路径和业务含义的前提下独立修订。涉及控件行为、信息可达性或操作后果的变化要先检查 UX 影响，不能以“纯视觉修改”跳过交互决定。

## 独立维护与引用关系

需求基线为 UX 提供业务依据；UX 为 UI 提供任务与交互依据；UI 还可直接引用必要的需求约束。需求、UX 和 UI 均可关联实现与验收证据。引用记录具体条目和有效版本，小幅修订可补充修订日期或文档提交；需要精确恢复时使用固定修订。

项目现有索引只登记三份正文的入口、范围与版本，不复制它们的正文。三种基线的维护人、确认时间和正式版本可以不同，不要求一次性共同定稿。各自的基线状态与实施对齐状态也分别维护：某份基线已确认不表示其他两份已确认，更不表示软件已经实现或验收通过。

```text
需求基线：REQ-A，版本 2，修订 r3
UX 基线：UX-A，版本 1，修订 r8；引用 REQ-A 版本 2 / r3
UI 基线：UI-A，版本 4，修订 r2；引用 UX-A 版本 1 / r8
```

以上只是独立版本及引用的表达示例，不规定版本格式，也不代表实际项目状态。工程标准、架构和 API 契约保留在所属文档中，作为关联依据引用；不把它们强塞进 UI 或 UX，也不新增第四种混合基线替代这三份正文。

## 日常维护与变更传播

1. 定位本次受影响的基线、范围和有效决定。已有确认直接引用；新提议与已确认正文分开，只有明确要求冻结时才标冻结。
2. 修改该基线自己的正文与变更记录。日常澄清和小改沿用其正式版本，记录修订日期、差异与确认依据；重大变更或明确要求独立保留时，归档该基线旧版并建立新版。其他基线不跟随自动升级版本。
3. 沿条目引用检查影响。需求变化检查关联 UX、UI、实现和验收；UX 变化检查关联 UI、实现和验收，并确认是否触及需求规则；UI 变化检查受影响实现与视觉核对项，涉及交互或业务含义时再反馈上游。
4. 记录每个受影响对象的差异、当前状态、下一步及关闭依据。收到上游确认修订时更新对应正文；需要上游补充方案时交接具体问题，暂停依赖部分，继续独立且获授权的工作。
5. 核对结果后只更新受影响的对齐记录。没有影响的基线保留正文、版本与仍有效的证据；存在影响但尚未更新的引用保留原版本并标记待对齐，不把它静默切换成最新版。

例如，上游只调整按钮颜色时修订 UI 及相关视觉核对记录；上游改变取消操作的确认步骤时修订 UX 并检查 UI；上游改变谁能取消时修订需求，再检查相应 UX、UI 与实现。三种变化均以有效决定为依据，不自动开始设计或实施。

## 三份独立正文模板

以下各是一份独立文档或独立可寻址的文档对象。字段可按范围裁剪，独立入口、确认依据与变更记录必须可定位。三个模板分别使用，不把它们放在同一正文中当作三个章节代替独立维护。

### 需求基线模板

```markdown
# 需求基线 <编号> <版本>

- 适用范围与排除项：
- 基线状态：草稿 / 已确认 / 被替代 / 已废弃
- 维护人、确认依据与日期：
- 当前正文入口、最近修订及历史入口：

## 已确认需求
| 需求编号 | 目标或业务规则 | 输入输出及边界 | 验收条件 | 来源与确认依据 |
| --- | --- | --- | --- | --- |

## 未决项与影响
<具体问题、受影响条目、承接方与下一步；已知决定和未知分别记录>

## 变更记录
<本基线的版本或修订、变化、原因、确认依据、受影响引用及替代关系>

## 对齐记录入口
<关联 UX、UI、实现和验收的记录；可引用项目现有任务>
```

### UX 基线模板

```markdown
# UX 基线 <编号> <版本>

- 适用范围与排除项：
- 基线状态：草稿 / 已确认 / 被替代 / 已废弃
- 维护人、确认依据与日期：
- 当前正文入口、最近修订及历史入口：
- 引用的需求基线及版本：

## 已确认任务与交互
| UX 编号 | 关联需求 | 用户任务与入口 | 操作路径与规则 | 反馈、异常与恢复 | 确认依据 |
| --- | --- | --- | --- | --- | --- |

## 信息结构与导航
<已确认的结构、返回和跨任务关系；图或说明可引用固定成员版本>

## 未决项、变更记录与对齐入口
<本基线独立记录；关联 UI、实现和验收，业务缺口交回需求决定方>
```

### UI 基线模板

```markdown
# UI 基线 <编号> <版本>

- 适用范围与排除项：
- 基线状态：草稿 / 已确认 / 被替代 / 已废弃
- 维护人、确认依据与日期：
- 当前正文入口、最近修订及历史入口：
- 引用的 UX 与必要需求基线及版本：

## 已确认界面呈现
| UI 编号 | 关联 UX 或需求 | 页面与区域 | 布局、组件与状态呈现 | 设计资产及版本 | 确认依据 |
| --- | --- | --- | --- | --- | --- |

## 视觉规范
<字体、颜色、间距、图标、组件变体与响应式规则；共享资产只引用权威入口>

## 未决项、变更记录与对齐入口
<本基线独立记录；关联实现和视觉核对，交互缺口交回 UX 决定方>
```

## 对齐状态与实施交接

按“基线条目及版本 × 对齐对象”记录状态，不用一枚全项目状态代替。可沿用未核对、待对齐、对齐中、待验证、已对齐、受阻、暂缓、不适用等项目已有名称；每个未关闭项有具体差异、下一步、关闭依据和必要的承接或恢复条件。承接方未知时如实记录。

依据变化时重新判断受影响的已对齐项，未受影响项保留有效证据。UI 对齐不证明 UX 路径符合要求，UX 对齐不证明业务规则已实现，构建通过也不证明三种基线均满足。没有运行验证时标明待验证，用户保留人工验证时交付具体检查内容。

交接说明当前采用的三份基线及版本、已完成事实、差异与下一步。版本不同或进度不同是正常状态，不为了让它们看起来一致而改写事实。基线维护完成不自动授权编码、发布或验收。

## 从旧基线拆分与历史归档

已有混合基线迁移时，先按上述职责将已确认条目分别归入需求、UX、UI，保留原条目与新条目的映射、确认依据和原有未决状态。只搬移和整理已有决定，不借拆分补作分析与设计。无法明确归属或规则冲突时记录问题交回上游。

确认本次拆分范围后，为三份正文分别登记现行入口和版本，更新当前引用；以固定文档修订或原有归档机制保留旧混合基线，并标注替代关系。历史任务继续按其原引用版本恢复，不能静默换成新基线。原有对齐状态逐项评估后迁移，不能因拆分完成就标全部已对齐。

以后只归档发生重大变更或被替代的那份基线，保留其原正文、引用版本、确认依据、当时状态、归档原因与后继入口。归档不等于删除；尚在其他范围有效的版本继续保留现行引用。重新采用历史内容应形成明确的新修订，不改写原历史。

## 完成依据与价值边界

本次涉及的基线各有独立且可恢复的正文、版本与确认记录；引用可追溯；变化及影响已记录；未决项、对齐状态与下一步清楚，即完成本次维护。没有 UX 或 UI 的范围有明确的不适用依据，缺失的必要成果仍作为缺口交接。

独立维护可减少把业务规则、交互行为和视觉呈现混为一体导致的改动扩散与版本混淆。既有基线管理有定性收益反馈；本次三基线拆分尚无量化收益或跨项目采用证据。维护成本主要是必要的引用、修订及差异记录，按范围裁剪。本方法不提供自动审批、跨平台同步、需求分析或设计生成。
