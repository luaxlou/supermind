# 需求基线协作与变更追踪

把已经达成共同理解的目标、范围、业务规则和验收条件形成可引用的现行版本，让设计、实现与验证有同一份依据。需求基线可以按授权修订；它不是把最初想法永久冻结，也不是现有代码功能的清单。

## 设计阶段的加载与持续使用

本方法属于设计阶段。实际进入设计阶段时，与 UI 基线方法一起加载，并读取采用方的现行需求和设计决定，构成整个阶段的持续语境。阶段内分析、设计、讨论、变更和验收对照都使用这份语境；不在每次动作或需求变化时重新查询能力库。

需求变化时更新项目基线及其影响，方法继续沿用。任务续接时恢复既有语境，只有正文丢失、方法需更换或出现未覆盖问题时才补读相关内容。需求基线为 UI 基线提供依据；无 UI 的设计仍使用需求基线，不创建无用页面。

## 何时使用

- 从需求讨论进入方案、模型、接口或 UI 设计，需要区分已确认事项与假设。
- 多角色、多模块或多轮协作中，需求散落、范围漂移、规则冲突或验收口径不一致。
- 已有系统新增或调整行为，需要判断影响并保留仍有效的承诺。

局部文案或已有行为契约内的微小修改，直接引用现有需求即可，不重建整套基线。探索性原型可以明确假设后继续探索；尚未达成决定的内容不能标成已确认。方法也适用于没有 UI 的接口、批处理和后台服务。

## 输入和输出

输入由采用方提供：当前用户目标、角色与场景、已有需求及最新决定、业务规则、系统边界、必要数据与质量约束、本次授权范围。现有实现只用于识别事实和差异，不能反向替用户决定需求。冲突材料需注明冲突点，不自动选择最新文件或现有代码为权威。

输出是可独立理解的需求正文、明确的现行版本与确认范围、待决事项、变更影响，以及需求到设计和验收的对应关系。沿用已有文档和标识；一个功能可以只维护一页，不要求创建额外管理系统。

## 如何采用

1. **提取目标和范围。** 写清谁在什么情况下完成什么任务，预期结果是什么，本次明确包含和不包含什么。将事实、建议、假设和有效决定分开；不能把参考图中的控件全部当成需求。
2. **形成可判断的需求项。** 给需要持续追踪的行为稳定编号，说明前置条件、输入、核心规则、结果、状态归属、权限和失败行为。数据口径、性能或可靠性要求只写已有依据的约束；“快速”“好用”等模糊表述先明确观察方式，不编造数值。
3. **补齐验收条件和冲突。** 用具体条件与可观察结果表达成功、失败和必要边界情境。区分业务上要求满足的行为与技术方案；只影响具体方案的待决项不阻止已经明确的范围继续设计，影响业务结果的冲突必须在依赖它的决定前解决。
4. **确认明确的范围。** 汇总影响用户结果的关键取舍，按已有决定和授权形成现行版本。确认可以针对子范围，不必等待全产品需求完备。AI 草稿、评审完成、用户确认、明确冻结分别表达；文档存在不等于用户已经确认，也不等于获准实施。
5. **让设计和验收引用它。** 将需求编号映射到用例、模型、规则、接口、页面区域和验收行为。一个需求可对应多处设计，一项共享设计可服务多个需求；没有页面的需求不强行映射 UI。设计补出新业务规则时，回到需求确认，不能只藏在图或代码中。
6. **处理变更并更新现行版本。** 对照原需求说明新增、调整或取消的行为、原因及受影响的设计、数据、实现和测试。授权明确则按范围更新；授权不足只澄清关键取舍。保留稳定编号和变更记录，取消项标明替代关系，不让多个文档各自维护不同“现行”正文。

基线更新后，逐项标注设计与实现的差异。已确认但未实现的需求仍是承诺，不伪装成已交付；已实现但未确认的行为也不能自动成为新承诺。旧证据是否仍有效取决于行为变化和覆盖范围，不由版本号单独决定。

## 可复制的最小模板

```markdown
# <范围>需求基线 <版本>

- 当前状态：草稿 / 已确认；冻结仅在明确决定后标记
- 确认范围及依据：<采用方有效决定，未确认部分分开列出>
- 用户目标和角色：<谁、情境、预期结果>
- 范围内 / 范围外：<本次承诺和明确排除项>
- 约束及依赖：<已有依据的规则、数据、质量条件和外部依赖>

## <REQ-编号> <行为名称>
- 场景与前置条件：<触发时机、角色、必要状态>
- 输入及业务规则：<由谁提供什么，按什么规则处理>
- 输出及状态归属：<结果、数据口径、改变谁的状态>
- 权限与异常：<不允许什么，失败时呈现和保留什么>
- 验收：给定 <条件>，当 <动作>，应观察到 <结果>
- 未决项：<缺失事实或选择；影响的决定和可继续范围>

| 需求编号 | 设计对应（可无 UI） | 验收行为 | 实现及证据状态 |
| --- | --- | --- | --- |
| <编号> | <用例/模型/接口/页面区域> | <可观察结果> | <未实现/待验证/已有证据> |

| 变更 | 原要求 → 新要求 | 原因和决定 | 影响项及待落实差异 |
| --- | --- | --- | --- |
| <编号> | <具体变化> | <依据及确认范围> | <设计、数据、实现、测试> |
```

按需要裁剪字段。模板中的角色、状态和编号形式均由采用方决定，不预设行业流程或统一审批机制。

## 与 UI 基线及其他设计的关系

需求基线描述业务结果、规则、范围和验收；UI 基线依赖当前范围已确认的需求基线，以线框图表达相应的信息层级、区域、控件与交互，供后续深化对照。模型、接口和系统设计分别承接其职责。它们通过需求编号和具体行为建立对应关系，不互相复制全文，也不以某一张图替代所有设计。

先确认足以支持当前设计的需求范围，再深化相关 UI 或接口；设计暴露新问题时可以返回需求修订，不强制单向瀑布流程。纯视觉调整且行为不变时更新 UI 基线即可；新增权限、改变状态含义、数据口径或取消能力时，需要同时更新需求及受影响的验收。

## 完成依据与边界

当前范围的目标和排除项明确；关键行为有可观察的验收条件；主要业务冲突已解决或显式限制了可继续范围；确认依据与未决项可区分；设计和验收能够追溯到现行要求。满足这些条件才可称该范围的需求基线已建立，不能据此宣称设计、实现或运行验证完成。

迁移时可配置角色、行业规则、系统形态、需求粒度、审批方式、质量指标和文档工具。固定要求是范围清楚、规则可理解、结果可验证、变更有依据、现行版本可定位。采用只需要本文和采用方自己的材料，不需要原始项目、私有会话或作者本机文件。

预期收益是减少范围漂移、设计漏项和验收争议；主要成本是必要的规则澄清及变更维护。当前方法经过内容审查与纸面推演，尚无实测跨项目成本收益数据。它不能替代领域专业判断，也不保证所有模糊需求都能在设计前一次性解决。
